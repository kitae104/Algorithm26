그리디 알고리즘

Greedy Algorithms

설계 기법 중급 Java 17+

미래를 전부 계산하지 않고 "지금 이 순간의 최선"만 반복해서 선택하는 전략, 그것이 그리디(탐욕) 알고리즘입니다. 이번 강의에서는 거스름돈과 회의실 배정 문제를 그리디로 해결하고, 그리디가 언제 통하고 언제 실패하는지를 실제 반례로 직접 확인합니다. 4강의 정렬과 6강의 우선순위 큐가 그리디의 핵심 도구로 다시 등장합니다.

이 강의의 목차

    01강의 소개

    이번 강의부터는 설계 기법을 배웁니다 — 특정 자료구조가 아니라 "어떤 전략으로 공략할 것인가"라는 사고방식입니다.

    • 지금까지: "모든 경우를 확인"(완전 탐색, DFS·BFS) 또는 "자료를 잘 정리"(정렬, 트리)하는 방식
    • 첫 번째 설계 기법 — 그리디(greedy, 탐욕) 알고리즘
      • 매 순간 눈앞의 최선을 선택하고, 한 번 한 선택은 절대 번복하지 않음
      • 덕분에 매우 빠르지만, 항상 전체 최적이 된다는 보장은 없음
    • 오늘의 진짜 주제 두 가지
      • 그리디로 문제를 푸는 방법(거스름돈, 회의실 배정, 작업 스케줄링)
      • 그리디를 써도 되는 문제인지 판별하는 눈 — 실패하는 반례를 완전 탐색(3강)으로 직접 찾아내며 기름

    오늘의 핵심 질문

    미래를 전부 따져 보지 않고 매 순간 눈앞의 최선만 골라도, 전체의 최선이 될까? 된다면 언제 되고, 안 된다면 왜 안 될까?

    04핵심 개념

    그리디 알고리즘이란?

    그리디 알고리즘은 매 단계에서 그 순간에 가장 좋아 보이는 선택을 하고, 한 번 한 선택은 절대 번복하지 않는 설계 기법 — 세 가지 특징이 있습니다.

    • 지역적 판단: 미래의 모든 경우를 계산하지 않고, 지금 보이는 정보만으로 결정합니다.
    • 번복 없음: 백트래킹(7강)처럼 되돌아가지 않습니다. 선택은 한 방향으로만 쌓입니다.
    • 빠름: 되돌아가지 않으므로 대개 정렬 한 번 + 순회 한 번이면 끝납니다.
    • 일상 속 그리디: 거스름돈 1,260원을 줄 때 누구나 가장 큰 500원부터 셉니다 — 500원 2개 → 100원 2개 → 50원 1개 → 10원 1개, 합계 6개. "매 순간 남은 금액을 가장 크게 줄이는 동전"을 고르는 것이 곧 그리디 선택입니다.

    그리디 설계 3단계

    단계할 일회의실 배정에서는
    1. 기준 정하기"지금의 최선"이 무엇인지 정의한다가장 일찍 끝나는 회의
    2. 최선을 빠르게 찾기정렬(4강) 또는 우선순위 큐(6강)를 사용한다종료 시각 오름차순 정렬
    3. 선택 반복하기순서대로 검토하며 조건에 맞으면 선택하고 넘어간다시작 시각 ≥ 마지막 종료 시각이면 선택
    • 2단계가 바로 이전 강의들이 필요한 이유 — 정렬해 두면 "앞에서부터 읽기"가 곧 "최선부터 검토하기"가 됨
    • 우선순위 큐를 쓰면 매 순간 최선을 O(log n)에 꺼낼 수 있음

    그리디가 실패하는 순간 — 반드시 알아야 할 반례

    어느 나라의 자판기가 동전 {1원, 7원, 10원}을 쓴다고 합시다 — 거스름돈 14원을 그리디(큰 동전부터)로 계산하면 어떻게 될까요?

    방법선택 과정동전 수
    그리디 (큰 동전부터)10원 1개 → 남은 4원을 1원 4개로5개
    최적해 (완전 탐색으로 확인)7원 2개2개
    실패의 원인
    • 지금의 최선(10원)을 집는 순간, 미래의 더 좋은 선택(7원 2개)이 불가능해짐
    • 7원은 10원의 배수 관계가 아니라서 "큰 동전을 포기하면 오히려 이득"인 경우가 생김
    • 그리디는 이런 문제에서 틀린 답을 아주 빠르게 내놓음
    • 이 수치(그리디 5개 vs 최적 2개)는 12 응용 예제에서 완전 탐색 코드로 직접 검증

    언제 그리디를 써도 되는가 — 탐욕 선택 속성

    그리디가 정답을 보장하려면 탐욕 선택 속성(greedy choice property)이 성립해야 합니다. 직관적으로 말하면 이렇습니다.

    탐욕 선택 속성 — 한 줄 판별법

    "지금의 최선을 선택해도, 미래에 얻을 수 있는 최선이 절대 줄어들지 않는가?" 이 질문에 '예'라고 답할 수 있어야 그리디를 써도 됩니다.

    • 회의실 배정 — 성립. 가장 일찍 끝나는 회의 대신 다른 회의를 골라 봐야 회의실이 더 늦게 비므로, 어떤 최적해가 있더라도 그 첫 회의를 "가장 일찍 끝나는 회의"로 바꿔치기해도 손해가 없습니다(교환해도 답의 개수가 줄지 않음).
    • 한국 동전 — 성립. 10·50·100·500원은 서로 배수 관계라 큰 동전 1개를 작은 동전들로 쪼개면 항상 개수가 늘어납니다. 큰 동전을 포기할 이유가 없습니다.
    • 동전 {1, 7, 10} — 불성립. 10원을 선택하면 7원 2개라는 더 좋은 미래가 사라집니다. 반례가 하나라도 있으면 그리디는 그 문제의 정답 전략이 아닙니다.

    실무 요령: 그리디가 떠오르면 작은 입력으로 반례를 먼저 찾아보고, 반례가 없다고 확신할 근거(배수 관계, 교환해도 손해 없음)를 말로 설명할 수 있을 때만 그리디를 채택하세요. 반례가 나오는 문제는 11강의 동적 계획법이 맡습니다.

    05단계별 동작 과정

    오늘 신청된 회의 6건 — 전략 기획(8~12시), 디자인 리뷰(9~10시), 개발 스탠드업(10~11시), 고객 미팅(11~13시), 채용 면접(12~14시), 팀 회고(13~15시) — 을 회의실 배정 그리디가 처리하는 모습을 단계별로 봅니다. 먼저 종료 시각 기준으로 정렬한 뒤, 앞에서부터 한 건씩 검토합니다. 검토 중 = 파란색(현재), 선택 확정 = 초록색 "선택", 겹쳐서 거절 = 붉은색 "탈락". 다음 단계 ▶ 버튼으로 진행하거나 "새 데이터" 버튼으로 무작위 회의 목록도 실험해 보세요.

    마지막 단계에서 확인할 수 있듯, 기본 데이터(회의 6건)에서는 검토 6번 만에 4개가 선택됩니다 — 각 회의를 딱 한 번씩만 검토하고 절대 되돌아가지 않으며, 이 시각화의 진행 순서는 07 실습 코드의 selectMeetings 실행 결과와 정확히 일치합니다.

    06의사코드

    코드를 쓰기 전에 두 그리디 알고리즘의 절차를 언어 중립적으로 정리합니다.

    • 의사코드 = 특정 언어 문법 대신 우리말에 가까운 문장으로 알고리즘의 순서를 적은 것
    • 읽는 법: x ← 값은 "x에 값을 저장한다", 들여쓰기는 "바로 위 줄 안에 포함된 작업", // 뒤는 설명(주석)
    • 만약 … 이면: / 아니면:은 조건에 따라 갈라지는 부분, 각 … 에 대해는 목록을 하나씩 꺼내 반복하는 부분

    활동 선택 — 회의실 배정 (Activity Selection)

    Pseudo 회의실 배정 (활동 선택) 
    알고리즘 SelectMeetings(meetings)
    meetings를 종료 시각(end) 오름차순으로 정렬한다      // 그리디의 전처리 (4강 정렬)
    selected ← 빈 목록
    lastEnd ← 아주 작은 값                              // 아직 선택한 회의 없음
    meetings의 각 회의 m에 대해 순서대로:
        만약 m.start ≥ lastEnd 이면:                    // 그리디 선택 조건
            selected에 m을 추가한다
            lastEnd ← m.end                             // 선택은 번복하지 않는다
        아니면:
            m을 건너뛴다 (탈락)                         // 겹치는 회의는 버린다
    selected를 반환한다

    그리디 동전 교환 (Greedy Coin Change)

    Pseudo 그리디 동전 교환 
    알고리즘 GreedyCoinChange(amount, coins)               // coins는 내림차순 (큰 동전부터)
    totalCount ← 0
    remaining ← amount
    coins의 각 동전 coin에 대해 (큰 것부터):
        count ← remaining ÷ coin 의 몫                  // 이 동전을 최대한 사용 (그리디 선택)
        totalCount ← totalCount + count
        remaining ← remaining을 coin으로 나눈 나머지    // 남은 금액만 다음 동전으로 넘김
    totalCount를 반환한다

    두 의사코드 비교

    • 두 알고리즘 모두 구조가 같음: 최선의 순서를 만들고(정렬/내림차순 동전) → 앞에서부터 최대한 선택한다
    • 반복문이 하나뿐이고 되돌아가는 고리가 없다는 점이 7강의 백트래킹과 결정적으로 다른 부분

    07실습 코드

    의사코드(06)를 Java로 옮깁니다. 오늘의 두 그리디 문제 — 회의실 배정과 거스름돈 1,260원 — 을 함께 해결하는 프로그램입니다.

    • sortByEndTime은 4강의 삽입 정렬을 그대로 재사용한 전처리(정렬)이고, selectMeetings의 if (m.start >= lastEnd) 한 줄이 04 핵심 개념·06 의사코드에서 말한 "검토하며 겹치지 않으면 무조건 선택"이라는 그리디 선택 그 자체
    • 동전 교환의 greedyCoinChange도 같은 구조 — 정렬(내림차순 배열) 후 큰 동전부터 순서대로 최대한 선택하는 반복문 하나
    • 동전 교환에서는 나눗셈(/)으로 "이 동전을 최대 몇 개 쓸 수 있는가"를, 나머지(%)로 "남은 금액"을 계산
    Java MeetingRoomComplete.java 
    import java.util.ArrayList;
import java.util.List;

public class MeetingRoomComplete {

    /** 회의 정보를 담는 작은 기록용 클래스 */
    static class Meeting {
        String name;
        int start;
        int end;

        Meeting(String name, int start, int end) {
            this.name = name;
            this.start = start;
            this.end = end;
        }
    }

    /** 그리디의 전처리: 4강의 삽입 정렬로 종료 시각 기준 오름차순 정렬 */
    static void sortByEndTime(Meeting[] meetings) {
        for (int i = 1; i < meetings.length; i++) {
            Meeting key = meetings[i];
            int j = i - 1;
            while (j >= 0 && meetings[j].end > key.end) {
                meetings[j + 1] = meetings[j];
                j--;
            }
            meetings[j + 1] = key;
        }
    }

    /** 그리디 선택: 일찍 끝나는 순서로 검토하며 겹치지 않으면 무조건 선택 */
    static List<Meeting> selectMeetings(Meeting[] sorted) {
        List<Meeting> selected = new ArrayList<>();
        int lastEnd = Integer.MIN_VALUE;

        for (Meeting m : sorted) {
            if (m.start >= lastEnd) {
                selected.add(m);
                lastEnd = m.end;
            }
        }
        return selected;
    }

    /** 그리디 동전 교환: 큰 동전부터 최대한 사용한다. coins는 내림차순 정렬 상태여야 한다. */
    static int greedyCoinChange(int amount, int[] coins) {
        int totalCount = 0;
        int remaining = amount;

        for (int coin : coins) {
            int count = remaining / coin;   // 이 동전을 최대 몇 개 쓸 수 있는가
            if (count > 0) {
                System.out.println("  " + coin + "원 x " + count + "개");
            }
            totalCount += count;
            remaining = remaining % coin;   // 남은 금액
        }
        return totalCount;
    }

    public static void main(String[] args) {
        // 문제 1: 회의실 배정
        Meeting[] meetings = {
            new Meeting("전략 기획", 8, 12),
            new Meeting("디자인 리뷰", 9, 10),
            new Meeting("개발 스탠드업", 10, 11),
            new Meeting("고객 미팅", 11, 13),
            new Meeting("채용 면접", 12, 14),
            new Meeting("팀 회고", 13, 15)
        };

        System.out.println("== 문제 1: 회의실 배정 (신청 " + meetings.length + "건) ==");
        sortByEndTime(meetings);
        List<Meeting> selected = selectMeetings(meetings);
        for (Meeting m : selected) {
            System.out.println("  선택: " + m.name + " (" + m.start + "시 ~ " + m.end + "시)");
        }
        System.out.println("최대 " + selected.size() + "개의 회의를 열 수 있습니다.");

        // 문제 2: 동전 교환 (한국 동전은 서로 배수 관계라 그리디가 항상 최적)
        System.out.println();
        int amount = 1260;
        int[] coins = {500, 100, 50, 10};   // 큰 동전부터 (내림차순)

        System.out.println("== 문제 2: " + amount + "원 거슬러 주기 ==");
        int coinCount = greedyCoinChange(amount, coins);
        System.out.println("총 동전 수: " + coinCount + "개");
    }
}

import java.util.List;

public class BuggyStartTimeSort {

    /** 회의 정보를 담는 작은 기록용 클래스 */
    static class Meeting {
        String name;
        int start;
        int end;

        Meeting(String name, int start, int end) {
            this.name = name;
            this.start = start;
            this.end = end;
        }
    }

    /** 시작 시각(start) 기준으로 정렬한다 */
    static void sortByStartTime(Meeting[] meetings) {
        for (int i = 1; i < meetings.length; i++) {
            Meeting key = meetings[i];
            int j = i - 1;
            while (j >= 0 && meetings[j].start > key.start) {
                meetings[j + 1] = meetings[j];
                j--;
            }
            meetings[j + 1] = key;
        }

        for (Meeting m : sorted) {
            if (m.start >= lastEnd) {
                selected.add(m);
                lastEnd = m.end;
            }
        }
        return selected;
    }

            new Meeting("팀 회고", 13, 15)

    09복잡도 및 특성 분석

    복잡도 분석 = "데이터가 많아지면 일이 얼마나 늘어나는가?"를 따져 보는 것. 어려운 수식 대신 "몇 번 비교·계산하는가"만 세어 봅니다.

    입력 크기 — 무엇이 많아지는가?

    • 회의실 배정: 회의 수 n — 신청이 많아질수록 일이 늘어남
    • 동전 교환: 동전 종류 수 k — 금액이 아니라 동전 종류가 늘어날 때 일이 늘어남 (한국 동전은 k = 4)

    주요 연산 — 무엇을 세는가?

    • 프로그램에서 가장 많이 반복되는 한 동작만 세면 충분
    • 회의 정렬: 두 회의의 종료 시각을 비교하는 한 번 (삽입 정렬의 meetings[j].end > key.end)
    • 그리디 선택: "겹치지 않는가?"를 묻는 m.start >= lastEnd 한 번 — 회의마다 정확히 1번
    • 동전 교환: 동전마다 나눗셈(/)·나머지(%) 한 번씩

    시간 복잡도 — 얼마나 오래 걸리는가?

    단계비교 횟수회의 6건일 때회의 1만 건일 때Big-O
    정렬 — 삽입 정렬 (07 실습 코드)최악 n(n-1)/2번15번약 5,000만 번O(n²)
    정렬 — Arrays.sort·스트림 sorted약 n × log₂n번약 16번약 13만 번O(n log n)
    그리디 선택회의마다 1번: n번6번1만 번O(n)
    (비교용) 완전 탐색 — 모든 회의 조합 확인조합 2ⁿ개64개3,000자리가 넘는 수O(2ⁿ)
    • 전체 시간은 정렬이 결정: 선택 자체는 회의마다 한 번씩만 보고 되돌아가지 않으므로 O(n)으로 매우 가벼움 — 그래서 정렬 방법만 바꿔도 전체가 O(n²) → O(n log n)으로 빨라짐
    • O(n²)을 쉽게 말하면: 회의가 10배 늘면 정렬 비교는 100배 늘어남 — 반 친구 모두가 서로 한 번씩 악수하는 것과 같음
    • O(n)을 쉽게 말하면: 회의가 10배 늘면 선택도 10배만 늘어남 — 출석부를 위에서부터 한 번 읽어 내려가는 것과 같음
    • 회의가 6건뿐이면 차이 없음: 15번과 16번 — 정렬 방법의 차이는 데이터가 많아질 때 비로소 드러남
    • 동전 교환은 O(k): 1,260원이든 126만 원이든 한국 동전 4종류마다 나눗셈 한 번씩, 딱 4번이면 끝 — 금액이 커져도 일은 그대로
    • 우선순위 큐 방식(12 응용 예제의 작업 스케줄링): 넣기·꺼내기가 각각 O(log n)이므로 작업 n개 전체는 O(n log n)

    공간 복잡도 — 메모리를 얼마나 더 쓰는가?

    • 회의실 배정: 선택된 회의를 담는 목록 — 최대 n개이므로 O(n) (삽입 정렬 자체는 배열 안에서 자리만 바꾸므로 추가 메모리 거의 없음)
    • 동전 교환: 남은 금액·합계 같은 변수 몇 개뿐 — 금액이 커져도 그대로, O(1)

    알고리즘 특성 — 언제 무엇을 쓰는가?

    • 번복 없음: 백트래킹(7강)과 달리 한 번 한 선택을 취소하지 않음 — 그래서 빠르지만, 기준이 잘못되면 만회할 기회도 없음
      • 비유: 산에서 눈앞의 가장 가파른 오르막만 따라 오르면 빨리 오르지만, 가까운 작은 봉우리에 올라 버리면 더 높은 봉우리로 돌아갈 수 없음
    • 정답 보장은 문제의 성질에 달림: 같은 코드가 한국 동전(1,260원 → 6개)에서는 최적, 동전 {1, 7, 10}(14원 → 5개, 최적은 2개)에서는 오답 — 알고리즘이 아니라 문제가 탐욕 선택 속성을 갖는지가 관건
    • 반례 하나면 탈락: "여러 번 해 보니 맞더라"로는 부족 — "반례가 있을 수 없다"는 근거(교환해도 손해 없음, 배수 관계)를 말할 수 있어야 그리디를 믿을 수 있음
    • 속도 대 정확성: 그리디 O(n log n)은 모든 조합을 보는 완전 탐색 O(2ⁿ)보다 압도적으로 빠름 — 정답이 보장되는 문제라면 그리디가 최고의 선택, 보장되지 않으면 11강의 동적 계획법으로
    한 줄 정리 — 빠른 것은 확실, 맞는지는 문제가 결정
    • 그리디는 정렬 한 번 + 한 번 훑기로 끝나 빠르지만(보통 O(n log n)), 그 답이 최선인지는 탐욕 선택 속성이 성립하는 문제에서만 보장됨

    10람다·스트림 변경

    07 실습 코드(MeetingRoomComplete.java)를 람다와 스트림으로 다시 쓴 코드입니다. 문법은 추가 정보의 람다식·자바 스트림 문서를 참고하세요.

    Java ModernizeSolution.java 
    import java.util.ArrayList;
import java.util.Arrays;
import java.util.Comparator;
import java.util.List;
import java.util.stream.IntStream;

/**
 * 10강 「람다·스트림 변경」.
 *
 * MeetingRoomComplete.java(실습 코드)를 같은 결과가 나오도록 람다와 스트림으로 다시 쓴 것이다.
 */
public class ModernizeSolution {

    /** 회의 정보를 담는 작은 기록용 클래스 */
    static class Meeting {
        String name;
        int start;
        int end;

        Meeting(String name, int start, int end) {
            this.name = name;
            this.start = start;
            this.end = end;
        }
    }

    /** 그리디의 전처리: 종료 시각 기준 오름차순으로 정렬한 새 목록을 만든다. */
    static List<Meeting> sortByEndTime(Meeting[] meetings) {
        return Arrays.stream(meetings)
                .sorted(Comparator.comparingInt(m -> m.end))
                .toList();
    }

    /** 그리디 선택: 일찍 끝나는 순서로 검토하며 겹치지 않으면 무조건 선택 */
    static List<Meeting> selectMeetings(List<Meeting> sorted) {
        List<Meeting> selected = new ArrayList<>();
        int lastEnd = Integer.MIN_VALUE;

        // lastEnd가 선택할 때마다 바뀌므로, 선택 단계는 반복문 그대로 둔다
        for (Meeting m : sorted) {
            if (m.start >= lastEnd) {
                selected.add(m);
                lastEnd = m.end;
            }
        }
        return selected;
    }

    /** 그리디 동전 교환: 큰 동전부터 최대한 사용한다. coins는 내림차순 정렬 상태여야 한다. */
    static int greedyCoinChange(int amount, int[] coins) {
        int[] counts = new int[coins.length];
        int remaining = amount;

        // remaining이 동전마다 바뀌므로, 개수 계산은 반복문 그대로 둔다
        for (int i = 0; i < coins.length; i++) {
            counts[i] = remaining / coins[i];   // 이 동전을 최대 몇 개 쓸 수 있는가
            remaining = remaining % coins[i];   // 남은 금액
        }

        // 1개 이상 쓴 동전만 골라 출력한다
        IntStream.range(0, coins.length)
                .filter(i -> counts[i] > 0)
                .forEach(i -> System.out.println("  " + coins[i] + "원 x " + counts[i] + "개"));

        return Arrays.stream(counts).sum();
    }

    public static void main(String[] args) {
        // 문제 1: 회의실 배정
        Meeting[] meetings = {
            new Meeting("전략 기획", 8, 12),
            new Meeting("디자인 리뷰", 9, 10),
            new Meeting("개발 스탠드업", 10, 11),
            new Meeting("고객 미팅", 11, 13),
            new Meeting("채용 면접", 12, 14),
            new Meeting("팀 회고", 13, 15)
        };

        System.out.println("== 문제 1: 회의실 배정 (신청 " + meetings.length + "건) ==");
        List<Meeting> sorted = sortByEndTime(meetings);
        List<Meeting> selected = selectMeetings(sorted);
        selected.forEach(m ->
                System.out.println("  선택: " + m.name + " (" + m.start + "시 ~ " + m.end + "시)"));
        System.out.println("최대 " + selected.size() + "개의 회의를 열 수 있습니다.");

        // 문제 2: 동전 교환 (한국 동전은 서로 배수 관계라 그리디가 항상 최적)
        System.out.println();
        int amount = 1260;
        int[] coins = {500, 100, 50, 10};   // 큰 동전부터 (내림차순)

        System.out.println("== 문제 2: " + amount + "원 거슬러 주기 ==");
        int coinCount = greedyCoinChange(amount, coins);
        System.out.println("총 동전 수: " + coinCount + "개");
    }
}

    문제 상황

    • 동네 인쇄소에 작업 4건 접수: 문서 인쇄 5분, 로고 시안 2분, 영상 렌더링 8분, 명함 수정 1분 — 프린터는 한 대뿐이라 한 번에 하나씩 처리
    • 손님들의 총 대기 시간을 최소로 만들려면 어떤 순서로 처리해야 할까? 그리디의 답: 가장 짧은 작업 먼저
    • 짧은 작업을 먼저 끝내면 뒤에서 기다리는 모든 손님의 대기가 함께 줄기 때문

    데이터 모델과 알고리즘 적용 기준

    • 데이터: 작업 이름과 소요 시간(분)을 담은 Job 객체 배열
    • 방법 1 (접수 순서): 비교 기준 — 들어온 순서. 아무 전략 없음.
    • 방법 2 (그리디): 매 순간 "남은 작업 중 가장 짧은 것"을 선택. 6강의 PriorityQueue에 4강의 Comparator.comparingInt로 기준을 주면 poll()이 매번 최단 작업을 꺼내 줍니다. (job -> job.minutes는 바로 앞 10 람다·스트림 변경에서 정렬 기준을 줄 때 쓴 것과 같은 람다 문법)
    Java ShortestJobApplication.java 
    import java.util.Comparator;
import java.util.PriorityQueue;

public class ShortestJobApplication {

    /** 작업 정보를 담는 작은 기록용 클래스 (이름, 소요 시간) */
    static class Job {
        String name;
        int minutes;

        Job(String name, int minutes) {
            this.name = name;
            this.minutes = minutes;
        }
    }

    /** 주어진 순서대로 처리했을 때 각 작업의 대기 시간과 총 대기 시간을 출력한다. */
    static int runInOrder(Job[] jobs) {
        int currentTime = 0;   // 지금까지 흐른 시간 = 다음 작업의 대기 시간
        int totalWait = 0;

        for (Job job : jobs) {
            System.out.println("  " + job.name + " (" + job.minutes
                    + "분) — 대기 " + currentTime + "분");
            totalWait += currentTime;
            currentTime += job.minutes;
        }
        System.out.println("  총 대기 시간: " + totalWait + "분");
        return totalWait;
    }

    public static void main(String[] args) {
        Job[] jobs = {
            new Job("문서 인쇄", 5),
            new Job("로고 시안", 2),
            new Job("영상 렌더링", 8),
            new Job("명함 수정", 1)
        };

        System.out.println("== 방법 1: 접수 순서대로 처리 ==");
        int waitInOrder = runInOrder(jobs);

        // 그리디: "가장 짧은 작업 먼저" — 6강의 우선순위 큐가 매 순간 최솟값을 꺼내 준다
        System.out.println();
        System.out.println("== 방법 2: 그리디 — 가장 짧은 작업 먼저 (PriorityQueue) ==");
        PriorityQueue<Job> queue =
                new PriorityQueue<>(Comparator.comparingInt(job -> job.minutes));
        for (Job job : jobs) {
            queue.offer(job);
        }

        int currentTime = 0;
        int totalWait = 0;
        while (!queue.isEmpty()) {
            Job job = queue.poll();   // 남은 작업 중 소요 시간이 가장 짧은 작업
            System.out.println("  " + job.name + " (" + job.minutes
                    + "분) — 대기 " + currentTime + "분");
            totalWait += currentTime;
            currentTime += job.minutes;
        }
        System.out.println("  총 대기 시간: " + totalWait + "분");

        System.out.println();
        System.out.println("접수 순서: 총 대기 " + waitInOrder + "분 / 짧은 작업 먼저: 총 대기 "
                + totalWait + "분");
        System.out.println("짧은 작업을 먼저 끝내면 뒤에서 기다리는 모든 작업의 대기가 줄어든다.");
    }
}

    코드 해설과 복잡도 분석

    • 총 대기 시간이 27분에서 12분으로 줄었습니다. 먼저 처리되는 작업의 소요 시간은 뒤에 남은 모든 작업의 대기에 더해지므로, 짧은 작업을 앞에 둘수록 유리합니다 — 이 문제는 교환 논증으로 탐욕 선택 속성이 성립합니다(긴 작업과 짧은 작업의 순서를 바꾸면 항상 총 대기가 줄거나 같음).
    • 정렬 대신 우선순위 큐를 쓴 이유: 작업이 실행 중에도 계속 접수되는 실제 상황에서는 전체를 다시 정렬하는 것보다 offer(O(log n))로 끼워 넣는 편이 자연스럽습니다.
    • 복잡도: offer와 poll이 각각 O(log n), 작업 n개 처리 전체는 O(n log n). 공간 O(n).

    Java GreedyFailApplication.java 
    public class GreedyFailApplication {

    /** 그리디 동전 교환: 큰 동전부터 최대한 사용하고, 과정을 출력한다. */
    static int greedyChange(int amount, int[] coinsDesc) {
        int remaining = amount;
        int totalCount = 0;

        for (int coin : coinsDesc) {
            int count = remaining / coin;
            if (count > 0) {
                System.out.println("  [그리디] " + coin + "원 x " + count
                        + "개 → 남은 금액 " + (remaining % coin) + "원");
            }
            totalCount += count;
            remaining = remaining % coin;
        }
        return totalCount;
    }

    /**
     * 완전 탐색(3강): 동전 {10, 7, 1}의 모든 개수 조합을 확인해 최소 동전 수를 찾는다.
     * 남는 금액은 1원으로 채우면 되므로 10원과 7원의 개수만 모두 시도한다.
     */
    static int bestChangeFor14(int amount) {
        int best = Integer.MAX_VALUE;
        int bestTen = 0, bestSeven = 0, bestOne = 0;

        for (int ten = 0; ten * 10 <= amount; ten++) {
            for (int seven = 0; ten * 10 + seven * 7 <= amount; seven++) {
                int one = amount - ten * 10 - seven * 7;   // 나머지는 전부 1원
                int total = ten + seven + one;
                if (total < best) {
                    best = total;
                    bestTen = ten;
                    bestSeven = seven;
                    bestOne = one;
                }
            }
        }
        System.out.println("  [완전 탐색] 10원 " + bestTen + "개, 7원 " + bestSeven
                + "개, 1원 " + bestOne + "개");
        return best;
    }

    public static void main(String[] args) {
        System.out.println("== 실험 1: 동전 {1, 7, 10}으로 14원 거슬러 주기 ==");
        int[] strangeCoins = {10, 7, 1};
        int greedyResult = greedyChange(14, strangeCoins);
        System.out.println("그리디 결과: " + greedyResult + "개");
        int bestResult = bestChangeFor14(14);
        System.out.println("최적 결과: " + bestResult + "개");

        if (greedyResult != bestResult) {
            System.out.println("→ 그리디(" + greedyResult + "개)는 최적(" + bestResult
                    + "개)이 아니다! 지금의 최선(10원)이 미래의 더 좋은 선택(7원 2개)을 막았다.");
        }

        System.out.println();
        System.out.println("== 실험 2: 동전 {10, 50, 100, 500}으로 1260원 거슬러 주기 ==");
        int[] koreanCoins = {500, 100, 50, 10};
        int koreanResult = greedyChange(1260, koreanCoins);
        System.out.println("그리디 결과: " + koreanResult + "개");
        System.out.println("→ 한국 동전은 작은 동전이 큰 동전의 약수(배수 관계)라서");
        System.out.println("  큰 동전을 포기해도 이득이 없다. 이런 구조에서는 그리디가 항상 최적이다.");
    }
}

    • 같은 그리디 코드(greedyChange)가 실험 1에서는 오답(5개 vs 2개), 실험 2에서는 정답(6개)을 냅니다. 코드가 아니라 동전 체계의 성질이 정답 여부를 결정합니다.

    • 이 반례 데이터(그리디 5개 vs 최적 2개)는 11강에서 동적 계획법이 어떻게 올바른 답을 내는지 보여 주는 출발점이 됩니다.

    import java.util.ArrayList;
import java.util.List;

public class MeetingSchedulerSolution {

    /** 모임 정보를 담는 작은 기록용 클래스 (이름, 시작 시각, 종료 시각) */
    static class Meeting {
        String name;
        int start;
        int end;

        Meeting(String name, int start, int end) {
            this.name = name;
            this.start = start;
            this.end = end;
        }
    }

    /** 1단계: 종료 시각(end) 기준 오름차순 정렬 — 4강 삽입 정렬 재사용 */
    static void sortByEndTime(Meeting[] meetings) {
        for (int i = 1; i < meetings.length; i++) {
            Meeting key = meetings[i];
            int j = i - 1;
            while (j >= 0 && meetings[j].end > key.end) {
                meetings[j + 1] = meetings[j];
                j--;
            }
            meetings[j + 1] = key;
        }
    }

    /** 2단계: 시작 시각이 마지막 종료 시각 이상이면 선택 가능 (인접 모임 허용) */
    static boolean canSelect(Meeting next, int lastEnd) {
        return next.start >= lastEnd;
    }

    /** 3단계: 정렬된 목록을 검토하며 겹치지 않는 모임을 최대한 선택하고, 과정을 출력한다. */
    static List<Meeting> selectMeetings(Meeting[] sorted) {
        List<Meeting> selected = new ArrayList<>();
        int lastEnd = Integer.MIN_VALUE;

        for (Meeting m : sorted) {
            if (canSelect(m, lastEnd)) {
                selected.add(m);
                lastEnd = m.end;
                System.out.println("선택: " + m.name + " (" + m.start + "시~" + m.end
                        + "시) → 마지막 종료 " + lastEnd + "시");
            } else {
                System.out.println("탈락: " + m.name + " (" + m.start + "시~" + m.end
                        + "시) — 시작 " + m.start + "시 < 마지막 종료 " + lastEnd + "시");
            }
        }
        return selected;
    }

    public static void main(String[] args) {
        // 동아리 방 사용 신청 7건
        Meeting[] meetings = {
            new Meeting("스터디", 9, 11),
            new Meeting("밴드 연습", 10, 12),
            new Meeting("코딩 모임", 11, 13),
            new Meeting("영화 감상", 12, 16),
            new Meeting("보드게임", 13, 14),
            new Meeting("발표 준비", 14, 16),
            new Meeting("저녁 모임", 16, 18)
        };

        System.out.println("== 동아리 방 예약 프로그램 ==");
        System.out.println("신청된 모임: " + meetings.length + "건");
        System.out.println();

        System.out.println("[1단계] 종료 시간 순 정렬 결과");
        sortByEndTime(meetings);
        for (Meeting m : meetings) {
            System.out.println(m.name + " (" + m.start + "시~" + m.end + "시)");
        }
        System.out.println();

        System.out.println("[2단계] 그리디 선택 과정");
        List<Meeting> selected = selectMeetings(meetings);
        System.out.println();

        StringBuilder names = new StringBuilder();
        for (int i = 0; i < selected.size(); i++) {
            if (i > 0) names.append(", ");
            names.append(selected.get(i).name);
        }
        System.out.println("[결과] 최대 " + selected.size() + "개 모임 배정: " + names);
    }

    구현 순서와 핵심 알고리즘 적용 부분

    1. sortByEndTime은 4강 삽입 정렬에서 비교 기준만 meetings[j].end > key.end로 바꾼 것입니다. 그리디의 성패를 가르는 "최선의 정의"가 이 한 줄에 들어 있습니다.
    2. canSelect의 >=가 인접 모임(발표 준비 16시 종료 → 저녁 모임 16시 시작)을 허용합니다. 판정 로직을 별도 메서드로 분리하면 경계 조건을 테스트하기 쉽습니다.
    3. selectMeetings는 정렬된 목록을 한 번만 순회합니다. 선택 시 lastEnd 갱신이 그리디의 "선택 번복 없음"을 코드로 구현한 부분입니다.
    4. 영화 감상(12~16시)이 보드게임(13~14시)보다 뒤에 정렬되는 것에 주목하세요. 일찍 시작하지만 늦게 끝나는 모임이 뒤로 밀리는 것이 종료 시각 정렬의 효과입니다.

    복잡도 분석

    • 삽입 정렬 O(n²) + 그리디 선택 O(n) = 전체 O(n²). Arrays.sort(추가 도전 1)로 바꾸면 O(n log n)까지 줄어듭니다.
    • 공간은 선택 목록 O(n). 정렬은 제자리에서 수행되므로 추가 공간 O(1)입니다.

    자주 발생하는 오류

    • 정렬 기준을 start로 쓰는 경우 — 오류 1에서 봤듯 배정 수가 크게 줄어듭니다.
    • canSelect를 >로 쓰는 경우 — 발표 준비와 저녁 모임 중 하나가 탈락합니다(오류 2).
    • lastEnd 갱신을 빠뜨리는 경우 — lastEnd가 초깃값에 머물러 모든 모임이 선택됩니다(겹침 무시).
    • 탈락한 모임을 다시 검토하려고 이중 반복문을 쓰는 경우 — 그리디는 한 번 순회로 충분하며, 되돌아가면 O(n²)이 됩니다.
