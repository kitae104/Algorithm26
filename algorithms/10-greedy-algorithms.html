그리디 알고리즘

Greedy Algorithms

설계 기법 중급 Java 17+

미래를 전부 계산하지 않고 "지금 이 순간의 최선"만 반복해서 선택하는 전략, 그것이 그리디(탐욕) 알고리즘입니다. 이번 강의에서는 거스름돈과 회의실 배정 문제를 그리디로 해결하고, 그리디가 언제 통하고 언제 실패하는지를 실제 반례로 직접 확인합니다. 4강의 정렬과 6강의 우선순위 큐가 그리디의 핵심 도구로 다시 등장합니다.

이 강의의 목차

    01강의 소개

    지금까지 배운 알고리즘들은 대부분 "모든 경우를 확인"하거나(완전 탐색, DFS·BFS) "자료를 잘 정리"하는(정렬, 트리) 방식이었습니다. 이번 강의부터는 설계 기법을 배웁니다. 설계 기법이란 특정 자료구조가 아니라, "문제를 어떤 전략으로 공략할 것인가"라는 사고방식입니다.

    첫 번째 설계 기법인 그리디(greedy, 탐욕) 알고리즘은 매 순간 눈앞의 최선을 선택하고, 한 번 한 선택은 절대 번복하지 않습니다. 덕분에 매우 빠르지만, 항상 전체 최적이 된다는 보장은 없습니다. 그래서 이번 강의의 진짜 주제는 두 가지입니다. 첫째, 그리디로 문제를 푸는 방법(거스름돈, 회의실 배정, 작업 스케줄링). 둘째, 그리디를 써도 되는 문제인지 판별하는 눈 — 그리디가 실패하는 반례를 완전 탐색(3강)으로 직접 찾아내며 기릅니다.

    02학습 목표

    이 강의를 마치면 다음을 할 수 있습니다.

    • 학생은 그리디 알고리즘의 두 가지 특징(매 순간 최선 선택, 선택 번복 없음)을 예를 들어 설명할 수 있다.
    • 학생은 회의실 배정 문제를 종료 시각 기준 정렬과 그리디 선택으로 구현할 수 있다.
    • 학생은 한국 동전(500·100·50·10원)의 거스름돈을 그리디로 계산하고, 그리디가 최적인 이유를 배수 관계로 설명할 수 있다.
    • 학생은 그리디가 실패하는 동전 반례(동전 {1, 7, 10}으로 14원)를 제시하고 완전 탐색 결과와 수치로 비교할 수 있다.
    • 학생은 우선순위 큐를 사용해 "가장 짧은 작업 먼저" 스케줄링을 구현하고 총 대기 시간 감소를 확인할 수 있다.
    • 학생은 새 문제를 만났을 때 그리디를 적용해도 되는지 작은 반례 실험으로 판단할 수 있다.

    04실제 문제 상황

    여러분은 직원 40명 규모 스타트업의 사내 시스템 개발자입니다. 회사에 회의실이 딱 하나뿐인데, 오늘 하루에만 회의 신청이 6건 들어왔습니다. 시간이 겹치는 신청이 많아서 전부 받을 수는 없습니다. 총무팀의 요구는 명확합니다. "겹치지 않게, 최대한 많은 회의를 배정해 주세요." 어떤 회의를 받고 어떤 회의를 거절해야 "최대한 많이"가 될까요? 그리고 그 선택 기준이 정말 최선이라는 걸 어떻게 확신할 수 있을까요?

    한편 1층 사내 카페의 키오스크도 여러분 담당입니다. 거스름돈 1,260원을 내줄 때 동전을 가장 적은 개수로 주려면 어떻게 계산해야 할까요? 두 문제 모두 "여러 선택지 중에서 무엇을 고를 것인가"라는 공통점이 있습니다.

    05사람이 직접 해결해 보기

    코드를 쓰기 전에 두 문제를 손으로 풀어 봅니다. 사실 여러분은 이미 그리디 알고리즘을 일상에서 쓰고 있습니다.

    문제 1 — 거스름돈 1,260원을 동전 몇 개로?

    STEP 1

    동전은 500원, 100원, 50원, 10원. 편의점 아르바이트 경험을 떠올려 보세요. 누구나 가장 큰 500원부터 셉니다: 500원 2개(1,000원) → 100원 2개(1,200원) → 50원 1개(1,250원) → 10원 1개(1,260원). 합계 6개.

    질문: 왜 우리는 자연스럽게 큰 동전부터 셀까요?

    큰 동전 하나가 작은 동전 여러 개를 대신하기 때문입니다. 500원 1개 대신 10원을 쓰면 50개가 필요합니다. "매 순간 남은 금액을 가장 크게 줄이는 선택" — 이것이 그리디 선택입니다. 실제로 10원짜리만 쓰면 같은 1,260원도 126개가 됩니다.

    STEP 2

    이 방법이 정말 최선일까요? 500원을 2개 대신 1개만 쓰고 나머지를 작은 동전으로 채우면 어떻게 되는지 따져 봅시다.

    질문: 500원을 하나 포기하면 동전 수는 어떻게 될까요?

    포기한 500원을 채우려면 최소한 100원 5개가 필요합니다. 1개를 포기하고 5개를 얻으니 항상 손해입니다. 한국 동전은 10 → 50 → 100 → 500이 전부 배수 관계라서, 큰 동전을 포기해서 이득을 보는 경우가 없습니다. 그래서 이 문제에서는 그리디가 항상 최적입니다. (배수 관계가 깨지면 어떻게 되는지는 핵심 개념에서 확인합니다.)

    문제 2 — 회의실 배정: 어떤 기준으로 고를까?

    오늘 신청된 회의 6건입니다. 시간이 겹치지 않게 최대한 많이 골라 보세요.

    회의시작종료
    전략 기획8시12시
    디자인 리뷰9시10시
    개발 스탠드업10시11시
    고객 미팅11시13시
    채용 면접12시14시
    팀 회고13시15시
    STEP 3

    기준 후보 1: "신청이 먼저 들어온 순서(목록 순서)대로" — 전략 기획(8~12시)부터 받아 봅시다.

    질문: 전략 기획을 받으면 몇 개나 배정할 수 있나요?

    전략 기획이 8~12시를 통째로 차지해서 디자인 리뷰, 개발 스탠드업, 고객 미팅이 전부 탈락합니다. 이후 채용 면접(12~14시)만 더 받을 수 있어 2개에 그칩니다. (팀 회고는 13시 시작이라 채용 면접과 겹칩니다.) 긴 회의 하나가 여러 짧은 회의의 자리를 빼앗았습니다.

    STEP 4

    기준 후보 2: "일찍 시작하는 회의부터" — 시작 시각 순으로 골라 봅시다.

    질문: 이 기준으로는 몇 개가 되나요?

    가장 일찍 시작하는 회의가 하필 전략 기획(8~12시)이라 결과는 똑같이 2개 (전략 기획, 채용 면접)입니다. "일찍 시작"은 "일찍 자리를 비워 준다"를 보장하지 않습니다 — 이 기준의 함정은 오류 찾기 섹션에서 코드로 다시 확인합니다.

    STEP 5

    기준 후보 3: "일찍 끝나는 회의부터" — 종료 시각 순으로 골라 봅시다. 디자인 리뷰(~10시)를 먼저 받고, 그다음부터는 겹치지 않는 것 중 가장 일찍 끝나는 회의를 계속 받습니다.

    질문: 이 기준으로는 몇 개가 되나요? 왜 이 기준이 잘 통할까요?

    디자인 리뷰(9~10) → 개발 스탠드업(10~11) → 고객 미팅(11~13) → 팀 회고(13~15), 총 4개!

    일찍 끝나는 회의를 고를수록 남은 시간이 가장 길게 확보되기 때문입니다. "지금 가장 일찍 끝나는 회의"보다 다른 회의를 골라 봐야 회의실이 더 늦게 비므로, 이 선택은 미래의 선택지를 절대 줄이지 않습니다. 이것이 오늘 배울 그리디의 성공 조건입니다.

    06핵심 개념

    그리디 알고리즘이란?

    그리디 알고리즘은 매 단계에서 그 순간에 가장 좋아 보이는 선택을 하고, 한 번 한 선택은 절대 번복하지 않는 설계 기법입니다. 세 가지 특징이 있습니다.

    • 지역적 판단: 미래의 모든 경우를 계산하지 않고, 지금 보이는 정보만으로 결정합니다.
    • 번복 없음: 백트래킹(7강)처럼 되돌아가지 않습니다. 선택은 한 방향으로만 쌓입니다.
    • 빠름: 되돌아가지 않으므로 대개 정렬 한 번 + 순회 한 번이면 끝납니다.

    그리디 설계 3단계

    단계할 일회의실 배정에서는
    1. 기준 정하기"지금의 최선"이 무엇인지 정의한다가장 일찍 끝나는 회의
    2. 최선을 빠르게 찾기정렬(4강) 또는 우선순위 큐(6강)를 사용한다종료 시각 오름차순 정렬
    3. 선택 반복하기순서대로 검토하며 조건에 맞으면 선택하고 넘어간다시작 시각 ≥ 마지막 종료 시각이면 선택

    2단계가 바로 이전 강의들이 필요한 이유입니다. 정렬해 두면 "앞에서부터 읽기"가 곧 "최선부터 검토하기"가 되고, 우선순위 큐를 쓰면 매 순간 최선을 O(log n)에 꺼낼 수 있습니다.

    그리디가 실패하는 순간 — 반드시 알아야 할 반례

    어느 나라의 자판기가 동전 {1원, 7원, 10원}을 쓴다고 합시다. 거스름돈 14원을 그리디(큰 동전부터)로 계산하면 어떻게 될까요?

    방법선택 과정동전 수
    그리디 (큰 동전부터)10원 1개 → 남은 4원을 1원 4개로5개
    최적해 (완전 탐색으로 확인)7원 2개2개
    실패의 원인

    지금의 최선(10원)을 집는 순간, 미래의 더 좋은 선택(7원 2개)이 불가능해졌습니다. 7원은 10원의 배수 관계가 아니라서 "큰 동전을 포기하면 오히려 이득"인 경우가 생긴 것입니다. 그리디는 이런 문제에서 틀린 답을 아주 빠르게 내놓습니다. 이 수치(그리디 5개 vs 최적 2개)는 응용 예제에서 완전 탐색 코드로 직접 검증합니다.

    언제 그리디를 써도 되는가 — 탐욕 선택 속성

    그리디가 정답을 보장하려면 탐욕 선택 속성(greedy choice property)이 성립해야 합니다. 직관적으로 말하면 이렇습니다.

    탐욕 선택 속성 — 한 줄 판별법

    "지금의 최선을 선택해도, 미래에 얻을 수 있는 최선이 절대 줄어들지 않는가?" 이 질문에 '예'라고 답할 수 있어야 그리디를 써도 됩니다.

    • 회의실 배정 — 성립. 가장 일찍 끝나는 회의 대신 다른 회의를 골라 봐야 회의실이 더 늦게 비므로, 어떤 최적해가 있더라도 그 첫 회의를 "가장 일찍 끝나는 회의"로 바꿔치기해도 손해가 없습니다(교환해도 답의 개수가 줄지 않음).
    • 한국 동전 — 성립. 10·50·100·500원은 서로 배수 관계라 큰 동전 1개를 작은 동전들로 쪼개면 항상 개수가 늘어납니다. 큰 동전을 포기할 이유가 없습니다.
    • 동전 {1, 7, 10} — 불성립. 10원을 선택하면 7원 2개라는 더 좋은 미래가 사라집니다. 반례가 하나라도 있으면 그리디는 그 문제의 정답 전략이 아닙니다.

    실무 요령은 이렇습니다. 그리디가 떠오르면 작은 입력으로 반례를 먼저 찾아보고, 반례가 없다고 확신할 근거(배수 관계, 교환해도 손해 없음)를 말로 설명할 수 있을 때만 그리디를 채택하세요. 반례가 나오는 문제는 11강의 동적 계획법이 맡습니다.

    07단계별 동작 과정

    회의실 배정 그리디가 실제로 일하는 모습을 단계별로 봅니다. 먼저 종료 시각 기준으로 정렬한 뒤, 앞에서부터 한 건씩 검토합니다. 검토 중인 회의는 파란색(현재), 선택된 회의는 초록색(확정) "선택", 겹쳐서 거절된 회의는 붉은색(오류) "탈락" 표시가 붙습니다. 다음 단계 ▶ 버튼으로 진행하고, "새 데이터" 버튼으로 무작위 회의 목록도 실험해 보세요.

    마지막 단계에서 확인할 수 있듯, 기본 데이터(회의 6건)에서는 검토 6번 만에 4개가 선택됩니다. 각 회의를 딱 한 번씩만 검토하고 절대 되돌아가지 않는 것 — 이 시각화의 진행 순서는 아래 실행 과정 추적 코드의 출력과 정확히 일치합니다.

    08의사코드

    코드를 쓰기 전에 두 그리디 알고리즘의 절차를 언어 중립적으로 정리합니다.

    Pseudo 회의실 배정 (활동 선택) 
    알고리즘 SelectMeetings(meetings)
    meetings를 종료 시각(end) 오름차순으로 정렬한다      // 그리디의 전처리 (4강 정렬)
    selected ← 빈 목록
    lastEnd ← 아주 작은 값                              // 아직 선택한 회의 없음
    meetings의 각 회의 m에 대해 순서대로:
        만약 m.start ≥ lastEnd 이면:                    // 그리디 선택 조건
            selected에 m을 추가한다
            lastEnd ← m.end                             // 선택은 번복하지 않는다
        아니면:
            m을 건너뛴다 (탈락)
    selected를 반환한다
    Pseudo 그리디 동전 교환 
    알고리즘 GreedyCoinChange(amount, coins)               // coins는 내림차순 (큰 동전부터)
    totalCount ← 0
    remaining ← amount
    coins의 각 동전 coin에 대해 (큰 것부터):
        count ← remaining ÷ coin 의 몫                  // 이 동전을 최대한 사용 (그리디 선택)
        totalCount ← totalCount + count
        remaining ← remaining을 coin으로 나눈 나머지
    totalCount를 반환한다

    두 알고리즘 모두 구조가 같습니다: 최선의 순서를 만들고(정렬/내림차순 동전) → 앞에서부터 최대한 선택한다. 반복문이 하나뿐이고 되돌아가는 고리가 없다는 점이 7강의 백트래킹과 결정적으로 다른 부분입니다.

    public class Step2OverlapCheck {

    Java Step3FirstPick.java 
    public class Step3FirstPick {

    /** 회의 정보를 담는 작은 기록용 클래스 */
    static class Meeting {
        String name;
        int start;
        int end;

        Meeting(String name, int start, int end) {
            this.name = name;
            this.start = start;
            this.end = end;
        }
    }

    /** 4강의 삽입 정렬을 재사용해 종료 시각(end) 기준 오름차순으로 정렬한다. */
    static void sortByEndTime(Meeting[] meetings) {
        for (int i = 1; i < meetings.length; i++) {
            Meeting key = meetings[i];
            int j = i - 1;
            // key보다 늦게 끝나는 회의를 한 칸씩 뒤로 민다
            while (j >= 0 && meetings[j].end > key.end) {
                meetings[j + 1] = meetings[j];
                j--;
            }
            meetings[j + 1] = key;
        }
    }

    public static void main(String[] args) {
        Meeting[] meetings = {
            new Meeting("전략 기획", 8, 12),
            new Meeting("디자인 리뷰", 9, 10),
            new Meeting("개발 스탠드업", 10, 11),
            new Meeting("고객 미팅", 11, 13),
            new Meeting("채용 면접", 12, 14),
            new Meeting("팀 회고", 13, 15)
        };

        sortByEndTime(meetings);

        System.out.println("[종료 시간 순 정렬 결과]");
        for (Meeting m : meetings) {
            System.out.println(m.name + " (" + m.start + "시 ~ " + m.end + "시)");
        }

        // 그리디의 첫 선택: 가장 일찍 끝나는 회의(정렬 후 첫 번째)를 무조건 선택한다

        System.out.println();

        // 다음 후보 하나만 판단해 본다: 시작 시각이 lastEnd 이상이면 함께 열 수 있다
        Meeting next = meetings[1];

            System.out.println("다음 후보 " + next.name + ": 시작 " + next.start
                    + "시 >= 마지막 종료 " + lastEnd + "시 → 선택 가능");

                    + "시 < 마지막 종료 " + lastEnd + "시 → 겹쳐서 탈락");
        }
    }
}

public class Step4GreedySelect {

    /** 회의 정보를 담는 작은 기록용 클래스 */
    static class Meeting {
        String name;
        int start;
        int end;

            this.name = name;
            this.start = start;
            this.end = end;
        }
    }

    /** 4강의 삽입 정렬을 재사용해 종료 시각 기준 오름차순으로 정렬한다. */
    static void sortByEndTime(Meeting[] meetings) {
        for (int i = 1; i < meetings.length; i++) {
            Meeting key = meetings[i];
            int j = i - 1;
            while (j >= 0 && meetings[j].end > key.end) {
                meetings[j + 1] = meetings[j];
                j--;
            }
            meetings[j + 1] = key;
        }
    }

    /** 정렬된 회의 목록에서 겹치지 않는 회의를 최대한 많이 선택한다. */
    static List<Meeting> selectMeetings(Meeting[] sorted) {

        int lastEnd = Integer.MIN_VALUE;   // 아직 아무 회의도 선택하지 않았다

            if (m.start >= lastEnd) {      // 그리디 선택: 겹치지 않으면 무조건 선택
                selected.add(m);
                lastEnd = m.end;           // 마지막 종료 시각을 갱신
            }
        }
        return selected;
    }

            new Meeting("채용 면접", 12, 14),
            new Meeting("팀 회고", 13, 15)
        };

        sortByEndTime(meetings);

    }

public class MeetingRoomComplete {

            Meeting key = meetings[i];
            int j = i - 1;
            while (j >= 0 && meetings[j].end > key.end) {
                meetings[j + 1] = meetings[j];

    static int greedyCoinChange(int amount, int[] coins) {
        int totalCount = 0;
        int remaining = amount;

        for (int coin : coins) {
            int count = remaining / coin;   // 이 동전을 최대 몇 개 쓸 수 있는가
            if (count > 0) {
                System.out.println("  " + coin + "원 x " + count + "개");
            }
            totalCount += count;
            remaining = remaining % coin;   // 남은 금액
        }
        return totalCount;
    }

    13복잡도 및 특성 분석

    입력 크기

    회의실 배정에서는 회의(활동)의 수 n, 동전 교환에서는 동전 종류의 수 k가 입력 크기입니다.

    주요 연산

    회의실 배정의 핵심 연산은 정렬의 비교·이동과 선택 단계의 비교 (m.start >= lastEnd, 회의당 정확히 1번)입니다. 동전 교환의 핵심 연산은 동전 종류당 나눗셈·나머지 1번씩입니다.

    시간 복잡도

    단계방법시간 복잡도
    정렬 (전처리)삽입 정렬 (이 강의의 구현)O(n²)
    정렬 (전처리)Arrays.sort + Comparator로 대체 시O(n log n)
    그리디 선택정렬된 목록 순회 — 회의당 비교 1번O(n)
    동전 교환동전 종류당 나눗셈·나머지 1번O(k)

    전체 시간은 정렬이 지배합니다. 선택 자체는 O(n)으로 매우 가볍습니다 — 한 번 선택하면 되돌아보지 않기 때문입니다. 우선순위 큐를 쓰는 방식(응용 예제)은 넣기·꺼내기가 각각 O(log n)이라 전체 O(n log n)입니다.

    공간 복잡도

    선택된 회의를 담는 목록이 최대 n개이므로 O(n), 동전 교환은 변수 몇 개만 쓰므로 O(1)입니다.

    알고리즘 특성

    • 번복 없음: 백트래킹(7강)과 달리 선택을 취소하지 않습니다. 그래서 빠르지만, 잘못된 기준이면 만회할 기회도 없습니다.
    • 정답 보장은 문제의 성질에 달렸다: 같은 코드라도 한국 동전에서는 최적, 동전 {1, 7, 10}에서는 오답입니다. 알고리즘이 아니라 문제가 탐욕 선택 속성을 갖는지가 관건입니다.
    • 반례 하나면 탈락: 그리디의 정당성은 "많은 경우 맞더라"가 아니라 "반례가 존재할 수 없다"는 논증(교환 논증, 배수 관계)으로만 확보됩니다.
    • 속도 대 정확성의 교환: 그리디 O(n log n)은 완전 탐색 O(2ⁿ)보다 압도적으로 빠릅니다. 정확성이 보장되는 문제라면 그리디가 최고의 선택입니다.

    응용 1 — 인쇄소 작업 스케줄링: 우선순위 큐로 그리디 하기

    문제 상황

    동네 인쇄소에 작업 4건이 접수되어 있습니다: 문서 인쇄 5분, 로고 시안 2분, 영상 렌더링 8분, 명함 수정 1분. 프린터는 한 대뿐이라 한 번에 하나씩 처리합니다. 손님들의 총 대기 시간을 최소로 만들려면 어떤 순서로 처리해야 할까요? 그리디의 답: 가장 짧은 작업 먼저. 짧은 작업을 먼저 끝내면 뒤에서 기다리는 모든 손님의 대기가 함께 줄기 때문입니다.

    데이터 모델과 알고리즘 적용 기준

    • 데이터: 작업 이름과 소요 시간(분)을 담은 Job 객체 배열
    • 방법 1 (접수 순서): 비교 기준 — 들어온 순서. 아무 전략 없음.
    • 방법 2 (그리디): 매 순간 "남은 작업 중 가장 짧은 것"을 선택. 6강의 PriorityQueue에 4강의 Comparator.comparingInt로 기준을 주면 poll()이 매번 최단 작업을 꺼내 줍니다.
    Java ShortestJobApplication.java 
    import java.util.Comparator;
import java.util.PriorityQueue;

public class ShortestJobApplication {

    /** 작업 정보를 담는 작은 기록용 클래스 (이름, 소요 시간) */
    static class Job {
        String name;
        int minutes;

        Job(String name, int minutes) {
            this.name = name;
            this.minutes = minutes;
        }
    }

    /** 주어진 순서대로 처리했을 때 각 작업의 대기 시간과 총 대기 시간을 출력한다. */
    static int runInOrder(Job[] jobs) {
        int currentTime = 0;   // 지금까지 흐른 시간 = 다음 작업의 대기 시간
        int totalWait = 0;

        for (Job job : jobs) {
            System.out.println("  " + job.name + " (" + job.minutes
                    + "분) — 대기 " + currentTime + "분");
            totalWait += currentTime;
            currentTime += job.minutes;
        }
        System.out.println("  총 대기 시간: " + totalWait + "분");
        return totalWait;
    }

    public static void main(String[] args) {
        Job[] jobs = {
            new Job("문서 인쇄", 5),
            new Job("로고 시안", 2),
            new Job("영상 렌더링", 8),
            new Job("명함 수정", 1)
        };

        System.out.println("== 방법 1: 접수 순서대로 처리 ==");
        int waitInOrder = runInOrder(jobs);

        // 그리디: "가장 짧은 작업 먼저" — 6강의 우선순위 큐가 매 순간 최솟값을 꺼내 준다
        System.out.println();
        System.out.println("== 방법 2: 그리디 — 가장 짧은 작업 먼저 (PriorityQueue) ==");
        PriorityQueue<Job> queue =
                new PriorityQueue<>(Comparator.comparingInt(job -> job.minutes));
        for (Job job : jobs) {
            queue.offer(job);
        }

        int currentTime = 0;
        int totalWait = 0;
        while (!queue.isEmpty()) {
            Job job = queue.poll();   // 남은 작업 중 소요 시간이 가장 짧은 작업
            System.out.println("  " + job.name + " (" + job.minutes
                    + "분) — 대기 " + currentTime + "분");
            totalWait += currentTime;
            currentTime += job.minutes;
        }
        System.out.println("  총 대기 시간: " + totalWait + "분");

        System.out.println();
        System.out.println("접수 순서: 총 대기 " + waitInOrder + "분 / 짧은 작업 먼저: 총 대기 "
                + totalWait + "분");
        System.out.println("짧은 작업을 먼저 끝내면 뒤에서 기다리는 모든 작업의 대기가 줄어든다.");
    }
}

    코드 해설과 복잡도 분석

    • 총 대기 시간이 27분에서 12분으로 줄었습니다. 먼저 처리되는 작업의 소요 시간은 뒤에 남은 모든 작업의 대기에 더해지므로, 짧은 작업을 앞에 둘수록 유리합니다 — 이 문제는 교환 논증으로 탐욕 선택 속성이 성립합니다(긴 작업과 짧은 작업의 순서를 바꾸면 항상 총 대기가 줄거나 같음).
    • 정렬 대신 우선순위 큐를 쓴 이유: 작업이 실행 중에도 계속 접수되는 실제 상황에서는 전체를 다시 정렬하는 것보다 offer(O(log n))로 끼워 넣는 편이 자연스럽습니다.
    • 복잡도: offer와 poll이 각각 O(log n), 작업 n개 처리 전체는 O(n log n). 공간 O(n).

    응용 2 — 그리디 실패 실험: 반례를 코드로 검증하기

    문제 상황

    핵심 개념에서 본 반례를 코드로 검증합니다. 동전 {1, 7, 10}으로 14원을 거슬러 줄 때, 같은 그리디 코드가 어떤 답을 내는지, 그리고 3강의 완전 탐색으로 찾은 진짜 최적해와 얼마나 차이 나는지 수치로 확인합니다.

    Java GreedyFailApplication.java 
    public class GreedyFailApplication {

    /** 그리디 동전 교환: 큰 동전부터 최대한 사용하고, 과정을 출력한다. */
    static int greedyChange(int amount, int[] coinsDesc) {
        int remaining = amount;
        int totalCount = 0;

        for (int coin : coinsDesc) {
            int count = remaining / coin;
            if (count > 0) {
                System.out.println("  [그리디] " + coin + "원 x " + count
                        + "개 → 남은 금액 " + (remaining % coin) + "원");
            }
            totalCount += count;
            remaining = remaining % coin;
        }
        return totalCount;
    }

    /**
     * 완전 탐색(3강): 동전 {10, 7, 1}의 모든 개수 조합을 확인해 최소 동전 수를 찾는다.
     * 남는 금액은 1원으로 채우면 되므로 10원과 7원의 개수만 모두 시도한다.
     */
    static int bestChangeFor14(int amount) {
        int best = Integer.MAX_VALUE;
        int bestTen = 0, bestSeven = 0, bestOne = 0;

        for (int ten = 0; ten * 10 <= amount; ten++) {
            for (int seven = 0; ten * 10 + seven * 7 <= amount; seven++) {
                int one = amount - ten * 10 - seven * 7;   // 나머지는 전부 1원
                int total = ten + seven + one;
                if (total < best) {
                    best = total;
                    bestTen = ten;
                    bestSeven = seven;
                    bestOne = one;
                }
            }
        }
        System.out.println("  [완전 탐색] 10원 " + bestTen + "개, 7원 " + bestSeven
                + "개, 1원 " + bestOne + "개");
        return best;
    }

    public static void main(String[] args) {
        System.out.println("== 실험 1: 동전 {1, 7, 10}으로 14원 거슬러 주기 ==");
        int[] strangeCoins = {10, 7, 1};
        int greedyResult = greedyChange(14, strangeCoins);
        System.out.println("그리디 결과: " + greedyResult + "개");
        int bestResult = bestChangeFor14(14);
        System.out.println("최적 결과: " + bestResult + "개");

        if (greedyResult != bestResult) {
            System.out.println("→ 그리디(" + greedyResult + "개)는 최적(" + bestResult
                    + "개)이 아니다! 지금의 최선(10원)이 미래의 더 좋은 선택(7원 2개)을 막았다.");
        }

        System.out.println();
        System.out.println("== 실험 2: 동전 {10, 50, 100, 500}으로 1260원 거슬러 주기 ==");
        int[] koreanCoins = {500, 100, 50, 10};
        int koreanResult = greedyChange(1260, koreanCoins);
        System.out.println("그리디 결과: " + koreanResult + "개");
        System.out.println("→ 한국 동전은 작은 동전이 큰 동전의 약수(배수 관계)라서");
        System.out.println("  큰 동전을 포기해도 이득이 없다. 이런 구조에서는 그리디가 항상 최적이다.");
    }
}

    코드 해설과 복잡도 분석

    • 같은 그리디 코드(greedyChange)가 실험 1에서는 오답(5개 vs 2개), 실험 2에서는 정답(6개)을 냅니다. 코드가 아니라 동전 체계의 성질이 정답 여부를 결정합니다.
    • 완전 탐색은 10원 개수 × 7원 개수의 모든 조합(각각 최대 amount/10, amount/7가지)을 확인하므로 O(amount²) 수준 — 느리지만 확실합니다. 빠른 알고리즘을 도입할 때는 느리지만 확실한 방법으로 결과를 검증하라는 1강의 원칙이 그리디 검증에도 그대로 적용됩니다.
    • 이 반례 데이터(그리디 5개 vs 최적 2개)는 11강에서 동적 계획법이 어떻게 올바른 답을 내는지 보여 주는 출발점이 됩니다.

    문제 제목 — 동아리 방 예약 도우미

    문제 배경

    여러분의 학교에는 동아리들이 함께 쓰는 공용 방이 하나 있습니다. 지금까지는 학생회가 신청서를 받아 손으로 시간표를 짰는데, 학기 초마다 "왜 우리 동아리만 떨어졌냐"는 항의가 끊이지 않았습니다. 학생회장이 여러분에게 부탁합니다. "겹치지 않게 최대한 많은 모임을 배정하고, 어떤 모임이 왜 탈락했는지 이유까지 출력되는 프로그램을 만들어 줘. 그래야 항의가 없지." 오늘 배운 회의실 배정 그리디가 정확히 이 문제입니다. 신청 7건을 종료 시각 순으로 정렬하고, 앞에서부터 그리디로 선택하면 됩니다.

    프로그램 목표

    모임 신청 목록을 입력받아 종료 시각 기준으로 정렬한 뒤, 겹치지 않는 모임을 최대한 선택하고 선택/탈락 과정과 최종 결과를 출력하는 콘솔 프로그램을 완성합니다.

    필수 요구사항

    1. sortByEndTime(Meeting[] meetings) — 종료 시각 오름차순 정렬을 삽입 정렬로 직접 구현한다. (Arrays.sort 사용 금지 — 비교 검증용으로는 허용)
    2. canSelect(Meeting next, int lastEnd) — 시작 시각이 마지막 종료 시각 이상이면 true를 반환한다.
    3. selectMeetings(Meeting[] sorted) — 정렬된 목록을 순서대로 검토하며 선택/탈락을 결정하고, 각 결정을 이유와 함께 출력한다.
    4. 탈락 출력에는 탈락 이유(시작 시각과 마지막 종료 시각의 비교)를 포함한다.

    Java MeetingSchedulerSolution.java 
    import java.util.ArrayList;
import java.util.List;

public class MeetingSchedulerSolution {

    /** 모임 정보를 담는 작은 기록용 클래스 (이름, 시작 시각, 종료 시각) */
    static class Meeting {
        String name;
        int start;
        int end;

        Meeting(String name, int start, int end) {
            this.name = name;
            this.start = start;
            this.end = end;
        }
    }

    /** 1단계: 종료 시각(end) 기준 오름차순 정렬 — 4강 삽입 정렬 재사용 */
    static void sortByEndTime(Meeting[] meetings) {
        for (int i = 1; i < meetings.length; i++) {
            Meeting key = meetings[i];
            int j = i - 1;
            while (j >= 0 && meetings[j].end > key.end) {
                meetings[j + 1] = meetings[j];
                j--;
            }
            meetings[j + 1] = key;
        }
    }

    /** 2단계: 시작 시각이 마지막 종료 시각 이상이면 선택 가능 (인접 모임 허용) */
    static boolean canSelect(Meeting next, int lastEnd) {
        return next.start >= lastEnd;
    }

    /** 3단계: 정렬된 목록을 검토하며 겹치지 않는 모임을 최대한 선택하고, 과정을 출력한다. */
    static List<Meeting> selectMeetings(Meeting[] sorted) {
        List<Meeting> selected = new ArrayList<>();
        int lastEnd = Integer.MIN_VALUE;

        for (Meeting m : sorted) {
            if (canSelect(m, lastEnd)) {
                selected.add(m);
                lastEnd = m.end;
                System.out.println("선택: " + m.name + " (" + m.start + "시~" + m.end
                        + "시) → 마지막 종료 " + lastEnd + "시");
            } else {
                System.out.println("탈락: " + m.name + " (" + m.start + "시~" + m.end
                        + "시) — 시작 " + m.start + "시 < 마지막 종료 " + lastEnd + "시");
            }
        }
        return selected;
    }

    public static void main(String[] args) {
        // 동아리 방 사용 신청 7건
        Meeting[] meetings = {
            new Meeting("스터디", 9, 11),
            new Meeting("밴드 연습", 10, 12),
            new Meeting("코딩 모임", 11, 13),
            new Meeting("영화 감상", 12, 16),
            new Meeting("보드게임", 13, 14),
            new Meeting("발표 준비", 14, 16),
            new Meeting("저녁 모임", 16, 18)
        };

        System.out.println("== 동아리 방 예약 프로그램 ==");
        System.out.println("신청된 모임: " + meetings.length + "건");
        System.out.println();

        System.out.println("[1단계] 종료 시간 순 정렬 결과");
        sortByEndTime(meetings);
        for (Meeting m : meetings) {
            System.out.println(m.name + " (" + m.start + "시~" + m.end + "시)");
        }
        System.out.println();

        System.out.println("[2단계] 그리디 선택 과정");
        List<Meeting> selected = selectMeetings(meetings);
        System.out.println();

        StringBuilder names = new StringBuilder();
        for (int i = 0; i < selected.size(); i++) {
            if (i > 0) names.append(", ");
            names.append(selected.get(i).name);
        }
        System.out.println("[결과] 최대 " + selected.size() + "개 모임 배정: " + names);

    1. sortByEndTime은 4강 삽입 정렬에서 비교 기준만 meetings[j].end > key.end로 바꾼 것입니다. 그리디의 성패를 가르는 "최선의 정의"가 이 한 줄에 들어 있습니다.
    2. canSelect의 >=가 인접 모임(발표 준비 16시 종료 → 저녁 모임 16시 시작)을 허용합니다. 판정 로직을 별도 메서드로 분리하면 경계 조건을 테스트하기 쉽습니다.
    3. selectMeetings는 정렬된 목록을 한 번만 순회합니다. 선택 시 lastEnd 갱신이 그리디의 "선택 번복 없음"을 코드로 구현한 부분입니다.

    복잡도 분석

    • 삽입 정렬 O(n²) + 그리디 선택 O(n) = 전체 O(n²). Arrays.sort(추가 도전 1)로 바꾸면 O(n log n)까지 줄어듭니다.
    • 공간은 선택 목록 O(n). 정렬은 제자리에서 수행되므로 추가 공간 O(1)입니다.

    자주 발생하는 오류

    • 정렬 기준을 start로 쓰는 경우 — 오류 1에서 봤듯 배정 수가 크게 줄어듭니다.
    • canSelect를 >로 쓰는 경우 — 발표 준비와 저녁 모임 중 하나가 탈락합니다(오류 2).
    • lastEnd 갱신을 빠뜨리는 경우 — lastEnd가 초깃값에 머물러 모든 모임이 선택됩니다(겹침 무시).
    • 탈락한 모임을 다시 검토하려고 이중 반복문을 쓰는 경우 — 그리디는 한 번 순회로 충분하며, 되돌아가면 O(n²)이 됩니다.

    기준을 바꿔도 정렬·선택은 그대로다

    for (int i = 1; i < meetings.length; i++) {
        Meeting key = meetings[i];
        int j = i - 1;
        while (j >= 0 && rule.compare(meetings[j], key) > 0) {

            j--;
        }

    수정 문제 ② — 종료 시각이 같은 회의는 누가 먼저인가

    • if 없이 조립으로 표현할 것
    • 힌트 — reversed()와 thenComparing()
