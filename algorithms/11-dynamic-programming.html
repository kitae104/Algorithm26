동적 계획법

Dynamic Programming

설계 기법 중급 Java 17+

7강의 재귀 피보나치는 n=35에서 약 3천만 번 호출됩니다. 같은 계산을 수백만 번 반복하기 때문입니다. 이번 강의에서는 "한 번 구한 답은 적어 두고 다시 쓴다"는 단순한 아이디어로 이 폭발을 잠재우는 동적 계획법(DP)을 배웁니다. 점화식을 세우는 3단계, 메모이제이션(탑다운)과 테이블(바텀업), 그리고 10강에서 그리디가 실패했던 동전 문제를 DP로 최적 해결하는 것까지 다룹니다.

    01강의 소개

    이번 강의는 자료구조가 아니라 "문제를 어떻게 설계하는가"를 다루는 설계 기법, 동적 계획법(DP)입니다.

    05핵심 개념

    동적 계획법(DP)이란?

    동적 계획법은 큰 문제를 작은 부분 문제로 나누고, 각 부분 문제의 답을 한 번만 계산해 저장한 뒤 재사용하는 설계 기법입니다.

    • 이름의 "동적(dynamic)"에 특별한 뜻은 없음 — 핵심은 "저장하고 재사용한다"뿐
    • 정렬이나 스택 같은 특정 알고리즘·자료구조가 아니라, 문제에 접근하는 방법 — 10강의 그리디와 같은 "설계 기법" 분류

    DP가 통하는 두 가지 조건

    조건뜻예시
    중복 부분 문제
    (Overlapping Subproblems)    		 같은 작은 문제가 여러 번 다시 등장한다 재귀 fibo(5)를 호출하면 fibo(3)이 2번, fibo(2)가 3번 다시 계산됨 (전체 호출 15번)
    최적 부분 구조
    (Optimal Substructure)    		 큰 문제의 (최적) 답을 작은 문제의 (최적) 답으로 조립할 수 있다 계단 4칸의 답(5) = 3칸의 답(3) + 2칸의 답(2)

    중복이 없다면 저장해 봐야 다시 쓸 일이 없고(그냥 분할 정복), 조립이 안 된다면 작은 답을 모아도 큰 답이 안 됩니다. 두 조건이 모두 성립할 때 DP가 위력을 발휘합니다.

    점화식 — DP의 설계도 (코드보다 먼저!)

    "작은 문제의 답으로 큰 문제의 답을 만드는 규칙"을 식으로 적은 것이 점화식입니다. 피보나치의 정의 자체가 점화식입니다: F(n) = F(n-1) + F(n-2), 그리고 F(0) = 0, F(1) = 1.

    • 계단 오르기는 정의가 식으로 주어지지 않으므로 우리가 유도해야 함 — 작은 예부터 살펴봄
      • 계단 4칸을 오르는 방법은 (1+1+1+1), (1+1+2), (1+2+1), (2+1+1), (2+2) — 모두 5가지
      • 마지막 걸음이 1칸인 것: (1+1+1+1), (1+2+1), (2+1+1) — 3가지, 앞부분은 정확히 "3칸을 오르는 방법"
      • 마지막 걸음이 2칸인 것: (1+1+2), (2+2) — 2가지, 앞부분은 정확히 "2칸을 오르는 방법"
    • 이 논리를 일반화: n칸에 도착하는 마지막 걸음은 반드시 1칸 아니면 2칸
    • 마지막이 1칸이면 그 앞은 "n-1칸을 오르는 모든 방법", 마지막이 2칸이면 "n-2칸을 오르는 모든 방법" — 두 묶음은 서로 겹치지 않음. 따라서:
    계단 오르기의 점화식
    • dp[n] = dp[n-1] + dp[n-2]  (단, dp[1] = 1, dp[2] = 2)
    • dp[n]은 "n칸 계단을 오르는 방법의 수" — 이 식이 확정되면 구현은 옮겨 적기에 가까움
    • DP 문제의 승부는 코드가 아니라 점화식에서 납니다.

    점화식을 세우는 3단계

    1. 정의 — dp[i]가 무엇인지 완전한 한국어 문장으로 적는다. (예: "dp[i] = i칸 계단을 오르는 방법의 수") 여기가 모호하면 다음 단계가 전부 무너집니다.
    2. 기저 조건 — 더 쪼갤 수 없는 가장 작은 문제의 답을 직접 적는다. (예: dp[1] = 1, dp[2] = 2) 7강 재귀의 기저 조건과 같은 역할입니다.
    3. 전이(점화식) — dp[i]를 이미 구한 앞의 답들로 만드는 규칙을 적는다. (예: dp[i] = dp[i-1] + dp[i-2]) "마지막 선택이 무엇이었나?"를 나눠 보는 것이 가장 흔한 요령입니다.

    같은 점화식, 두 가지 구현 — 메모이제이션 vs 타뷸레이션

    점화식이 정해지면 구현 방향은 두 가지 — 위에서 내려가며 필요할 때 계산하거나, 아래에서 올라가며 미리 다 채우거나.

    구분메모이제이션 (탑다운)타뷸레이션 (바텀업)
    방향큰 문제 → 작은 문제 (필요한 것만)작은 문제 → 큰 문제 (차례로 전부)
    구현 형태재귀 + 저장 배열(memo)반복문 + 테이블(dp)
    계산 범위실제로 필요한 부분 문제만 계산기저부터 목표까지 모든 칸을 계산
    호출 스택재귀 깊이만큼 사용 (아주 큰 n에서는 StackOverflow 위험)사용하지 않음 (반복문)
    코드 느낌점화식 정의를 거의 그대로 옮김 — 직관적채우는 순서를 직접 정해야 함 — 대신 빠르고 안전
    이 강의에서실습 코드의 waysByMemo실습 코드의 waysByTable 이후 기본 방식

    그리디(10강)와 DP의 차이

    • 그리디는 매 순간 하나의 선택을 확정하고 되돌리지 않음
    • DP는 각 부분 문제에서 가능한 모든 선택을 점화식으로 비교한 뒤 가장 좋은 답만 기록
    • 동전 문제로 말하면 — 그리디는 "일단 100원!"이지만, DP의 점화식 dp[금액] = min(dp[금액 - 동전] + 1)은 모든 동전을 다 넣어 보고 최소를 고름
    • 그래서 그리디가 실패하는 동전 {1, 60, 100}에서도 DP는 항상 최적(11번 응용 섹션에서 실측으로 확인)

    06단계별 동작 과정

    • 계단 8칸(dp[1] = 1, dp[2] = 2에서 시작)의 DP 테이블이 채워지는 과정을 단계별로 확인 — 다음 단계 ▶ 버튼으로 진행
    • 결과는 1, 2, 3, 5, 8, 13, 21, 34 — 8칸 계단을 오르는 방법은 34가지이고, 34가지를 일일이 나열하지 않고 덧셈 6번으로 끝남
    • 지금 계산 중인 칸은 파란색(현재), 점화식이 참조하는 앞의 두 칸은 앰버색(참조), 값이 확정된 칸은 초록색(확정)
    • 매 단계에서 하는 일은 단 하나 — 이미 확정된 두 칸을 더해 다음 칸을 채우는 것
    • 재귀처럼 위에서 내려갔다 올라오는 여행이 없고, 왼쪽에서 오른쪽으로 한 번 지나가면 끝
    • 이 "표 채우기"가 바로 바텀업 DP이고, 실습 코드의 waysByTable과 정확히 같은 동작

    07의사코드

    점화식 3단계를 그대로 의사코드로 옮깁니다. 두 구현 방향을 나란히 봅니다.

    • 의사코드 = 특정 언어 문법 대신 우리말에 가까운 문장으로 알고리즘의 순서를 적은 것
    • 읽는 법: x ← 값은 "x에 값을 저장한다", 들여쓰기는 "바로 위 줄 안에 포함된 작업", // 뒤는 설명(주석)
    • Ways(n-1)처럼 알고리즘이 자기 자신을 다시 부르는 것이 재귀(7강), memo[n]·dp[i]는 답을 적어 두는 배열의 칸
    Pseudo 방향 1 — 메모이제이션 (탑다운) 
    알고리즘 Ways(n)                      // dp 정의: n칸을 오르는 방법의 수
    n이 1이면 1을 반환한다             // 기저 조건
    n이 2이면 2를 반환한다
    memo[n]에 답이 있으면 그것을 반환한다   // 저장된 답 재사용 (중복 계산 제거)
    memo[n] ← Ways(n-1) + Ways(n-2)   // 전이(점화식) 결과를 저장
    memo[n]을 반환한다

    코드 설명 — 방향 1 메모이제이션

    • 알고리즘 Ways(n) — "n칸 계단을 오르는 방법의 수"를 돌려주는 알고리즘. 점화식 3단계의 ① 정의가 곧 이 알고리즘이 하는 일
    • n이 1이면 1을 반환한다, n이 2이면 2를 반환한다 — ② 기저 조건. 더 쪼개지 않고 답을 바로 돌려줌
      • 이 두 줄이 없으면 재귀가 멈추지 않고 n = 0, -1, … 로 계속 내려감 (09 오류 1이 바로 이 실수)
    • memo[n]에 답이 있으면 그것을 반환한다 — 메모이제이션의 핵심. 전에 한 번 구한 답이면 다시 계산하지 않고 적어 둔 값을 꺼냄
      • 수첩에 "Ways(3) = 3"이라고 적혀 있으면, 다음에 Ways(3)이 필요할 때 수첩만 펼쳐 보는 것과 같음
      • 이 한 줄 덕분에 각 Ways(k)는 딱 한 번만 실제로 계산됨 — 순수 재귀의 중복 계산이 사라짐
    • memo[n] ← Ways(n-1) + Ways(n-2) — ③ 전이. 작은 두 문제의 답을 재귀로 구해 더하고, 그 결과를 memo[n]에 저장
      • 순수 재귀와의 차이는 "계산 결과를 버리지 않고 적어 둔다"는 것 하나뿐
    • memo[n]을 반환한다 — 방금 저장한 답을 돌려줌. 다음에 같은 n이 오면 위의 "답이 있으면 반환" 줄에서 바로 끝남
    • 큰 문제(n)에서 출발해 필요한 작은 문제로 내려가며 풀기 때문에 "탑다운"
    Pseudo 방향 2 — 타뷸레이션 (바텀업) 
    알고리즘 WaysByTable(n)
    dp ← 크기 n+1의 표
    dp[1] ← 1                         // 기저 조건을 표에 먼저 적는다
    dp[2] ← 2
    i를 3부터 n까지 반복:
        dp[i] ← dp[i-1] + dp[i-2]     // 전이: 이미 채운 두 칸을 더한다
    dp[n]을 반환한다                   // 표의 마지막 칸이 최종 답

    코드 설명 — 방향 2 타뷸레이션

    • dp ← 크기 n+1의 표 — 답을 적어 둘 빈 표를 준비. dp[1]부터 dp[n]까지 쓰려면 인덱스 n이 있어야 하므로 크기는 n+1
      • 크기를 n으로 잡으면 dp[n]에서 배열 범위를 벗어남 (09 오류 2가 바로 이 실수)
    • dp[1] ← 1, dp[2] ← 2 — ② 기저 조건을 표의 첫 칸들에 먼저 적어 둠 (1칸은 [1] 한 가지, 2칸은 [1+1], [2] 두 가지)
    • i를 3부터 n까지 반복 — 작은 칸부터 큰 칸 쪽으로 차례대로 채움
      • 이 순서가 중요: dp[i]를 채울 때 필요한 dp[i-1], dp[i-2]는 이미 앞에서 채워져 있음
    • dp[i] ← dp[i-1] + dp[i-2] — ③ 전이. 이미 채운 앞의 두 칸을 더해 현재 칸을 채움
      • 예: dp[3] = 2 + 1 = 3, dp[4] = 3 + 2 = 5, dp[5] = 5 + 3 = 8, …
    • dp[n]을 반환한다 — 반복이 끝나면 표의 마지막 칸 dp[n]이 바로 n칸 계단의 답
    • 재귀 호출이 전혀 없고 반복문 하나로 작은 문제부터 올라가며 채우기 때문에 "바텀업"

    두 의사코드 비교

    • 두 의사코드의 점화식은 완전히 같음 — 다른 것은 계산 순서뿐
    • 탑다운(메모이제이션)은 "필요하면 내려가서 구해 오기" — 재귀 + 수첩(memo)
    • 바텀업(타뷸레이션)은 "아래부터 미리 다 채워 두기" — 반복문 + 표(dp)

    08실습 코드

    의사코드(07)의 두 방향을 그대로 Java로 옮겨, 계단 오르기를 네 가지 방법으로 구현하고 서로 검증하는 프로그램입니다.

    • waysByRecursion은 07 의사코드의 점화식을 그대로 재귀로 옮긴 것, waysByMemo는 같은 점화식에 메모이제이션(05 핵심 개념의 "저장하고 재사용")을 더한 탑다운 구현
    • waysByTable은 타뷸레이션(바텀업) — 05에서 다룬 "기저 조건부터 차례로 채우기"를 그대로 반복문으로 옮긴 것
    • waysByTwoVars는 새로 등장하는 공간 최적화 — 점화식이 직전 두 칸만 참조하므로 표 전체 대신 변수 2개만 유지해도 됨
    • 네 방법의 결과를 모두 비교해 다르면 경고를 출력 — 정확성 검증도 함께 함
    Java ClimbStairsComplete.java 
    public class ClimbStairsComplete {

    /** 방법별 호출/연산 횟수 카운터 */
    static long recursionCalls = 0;
    static long memoCalls = 0;

    /** 방법 1: 순수 재귀 — 점화식 그대로. 느리다(중복 계산). */
    static long waysByRecursion(int n) {
        recursionCalls++;
        if (n == 1) {
            return 1;
        }
        if (n == 2) {
            return 2;
        }
        return waysByRecursion(n - 1) + waysByRecursion(n - 2);
    }

    /** 방법 2: 메모이제이션(탑다운) — 계산한 답을 저장한다. */
    static long waysByMemo(int n) {
        long[] memo = new long[n + 1];
        return memoHelper(n, memo);
    }

    static long memoHelper(int n, long[] memo) {
        memoCalls++;
        if (n == 1) {
            return 1;
        }
        if (n == 2) {
            return 2;
        }
        if (memo[n] != 0) {
            return memo[n];
        }
        memo[n] = memoHelper(n - 1, memo) + memoHelper(n - 2, memo);
        return memo[n];
    }

    /** 방법 3: 타뷸레이션(바텀업) — 표를 앞에서부터 채운다. */
    static long waysByTable(int n) {
        if (n == 1) {
            return 1;
        }
        long[] dp = new long[n + 1];
        dp[1] = 1;
        dp[2] = 2;
        for (int i = 3; i <= n; i++) {
            dp[i] = dp[i - 1] + dp[i - 2];
        }
        return dp[n];
    }

    /** 방법 4: 공간 최적화 — 항상 직전 두 칸만 쓰므로 변수 2개면 충분하다. */
    static long waysByTwoVars(int n) {
        if (n == 1) {
            return 1;
        }
        long prev2 = 1;                     // dp[i - 2] 역할
        long prev1 = 2;                     // dp[i - 1] 역할
        for (int i = 3; i <= n; i++) {
            long current = prev1 + prev2;   // 같은 점화식
            prev2 = prev1;                  // 두 변수를 한 칸씩 밀어 준다
            prev1 = current;
        }
        return prev1;
    }

    public static void main(String[] args) {
        int[] sizes = {10, 20, 30};

        System.out.println("== 계단 오르기: 네 가지 구현 비교 ==");
        System.out.println("n    | 결과      | 재귀 호출    | 메모 호출 | 테이블 덧셈");
        System.out.println("-----+-----------+-------------+----------+------------");

        for (int n : sizes) {
            recursionCalls = 0;
            memoCalls = 0;
            long r1 = waysByRecursion(n);
            long r2 = waysByMemo(n);
            long r3 = waysByTable(n);
            long r4 = waysByTwoVars(n);

            System.out.printf("%-4d | %-9d | %,-11d | %-8d | %d%n",
                    n, r1, recursionCalls, memoCalls, n - 2);

            // 네 방법의 결과가 모두 같은지 정확성을 검증한다 (1강의 원칙)
            if (r1 != r2 || r1 != r3 || r1 != r4) {
                System.out.println("경고: 결과가 서로 다릅니다! 구현에 오류가 있습니다.");
            }
        }

        System.out.println();
        System.out.println("== 큰 입력: n = 50 (순수 재귀는 약 252억 번 호출이라 생략) ==");
        memoCalls = 0;
        System.out.println("메모이제이션 : " + waysByMemo(50) + " (호출 " + memoCalls + "번)");
        System.out.println("타뷸레이션   : " + waysByTable(50) + " (덧셈 48번, 표 51칸)");
        System.out.println("공간 최적화  : " + waysByTwoVars(50) + " (덧셈 48번, 변수 2개)");
        System.out.println();
        System.out.println("시간: O(2^n) → O(n), 공간: 테이블 O(n) → 변수 2개 O(1)");
    }
}

    공간 최적화는 언제 가능한가?

    • 최적화 전에 항상 "무엇을 참조하는가"를 먼저 확인할 것

    09잘못된 코드와 오류 찾기

    DP를 처음 배울 때 가장 자주 나는 오류 두 가지입니다. 먼저 코드를 읽고 무엇이 잘못됐는지 생각한 뒤 해설을 여세요.

    오류 1 — 기저 조건이 없는 메모이제이션

    Java BuggyFiboNoBase.java (오류 있음) 
    public class BuggyFiboNoBase {

    static long[] memo;

    /** 메모이제이션 피보나치 — 그런데 무언가 빠졌다! */
    static long fibo(int n) {
        if (memo[n] != 0) {
            return memo[n];
        }
        memo[n] = fibo(n - 1) + fibo(n - 2);
        return memo[n];
    }

    public static void main(String[] args) {
        int n = 30;
        memo = new long[n + 1];
        System.out.println("fibo(" + n + ") = " + fibo(n));
    }
}
    발생하는 문제와 수정 방법 확인
    • 발생하는 문제: 실행하면 답 대신 예외가 남
    Exception in thread "main" java.lang.ArrayIndexOutOfBoundsException: Index -1 out of bounds for length 31
	at BuggyFiboNoBase.fibo(BuggyFiboNoBase.java:7)
	at BuggyFiboNoBase.fibo(BuggyFiboNoBase.java:10)
	...(fibo가 fibo를 부르는 줄이 계속 이어짐)
    • 원인: 기저 조건이 없음 — 재귀가 멈출 곳이 없어 n = 1 → 0 → -1까지 내려가고, memo[-1]에서 음수 인덱스 예외가 남 (memo 배열조차 없었다면 7강에서 본 StackOverflowError가 났을 것)
    • 메모이제이션은 재귀 — 저장 로직을 추가해도 기저 조건은 여전히 필수
    • 수정 방법: 메모 확인보다 먼저 기저 조건을 처리
    static long fibo(int n) {
    if (n <= 1) {
        return n;          // 기저 조건이 가장 먼저!
    }
    if (memo[n] != 0) {
        return memo[n];
    }
    memo[n] = fibo(n - 1) + fibo(n - 2);
    return memo[n];
}

    수정 후 출력: fibo(30) = 832040. 점화식 3단계에서 기저 조건이 ② 단계로 따로 있는 이유가 이것입니다.

    오류 2 — 테이블 크기: n일까 n + 1일까

    Java BuggyTableSize.java (오류 있음) 
    public class BuggyTableSize {
    public static void main(String[] args) {
        int n = 10;
        long[] dp = new long[n];        // dp[0]부터 dp[n]까지 쓸 계획인데...
        dp[0] = 0;
        dp[1] = 1;
        for (int i = 2; i <= n; i++) {
            dp[i] = dp[i - 1] + dp[i - 2];
        }
        System.out.println("fibo(" + n + ") = " + dp[n]);
    }
}
    발생하는 문제와 수정 방법 확인
    • 발생하는 문제: 마지막 회차(i = 10)에서 예외가 남
    Exception in thread "main" java.lang.ArrayIndexOutOfBoundsException: Index 10 out of bounds for length 10
	at BuggyTableSize.main(BuggyTableSize.java:8)
    • 원인: 인덱스 0부터 n까지 쓰려면 칸이 n + 1개 필요한데 new long[n]은 0부터 n-1까지, n칸뿐 — 2강에서 배운 "배열 크기 vs 마지막 인덱스"의 off-by-one이 DP 테이블에서 그대로 재현된 것
    • dp[n]까지 쓰는 DP에서 아주 흔한 실수
    • 수정 방법: 테이블 크기를 n + 1로 잡음
    long[] dp = new long[n + 1];   // 인덱스 0 ~ n → 크기 n + 1

    수정 후 출력: fibo(10) = 55. 테이블을 선언할 때마다 "몇 번 인덱스까지 쓰는가?"를 소리 내어 확인하는 습관을 들이세요.

    10복잡도 및 특성 분석

    복잡도 분석 = "문제가 커지면 일이 얼마나 늘어나는가?"를 따져 보는 것. 어려운 수식 대신 "몇 번 계산하는가"만 세어 봅니다.

    입력 크기 — 무엇이 많아지는가?

    • 계단 오르기·피보나치: n — 계단이 몇 칸인지(피보나치라면 몇 번째 수인지). 칸이 많아질수록 일이 늘어남
    • 동전 문제(11번 섹션): 크기가 두 개 — 거슬러 줄 금액과 동전 종류 수

    주요 연산 — 무엇을 세는가?

    • 프로그램에서 가장 많이 반복되는 한 동작만 세면 충분
    • 재귀·메모이제이션: 함수를 한 번 부르는 것(호출 1번)
    • 타뷸레이션·공간 최적화: 표의 칸 하나를 채우는 덧셈 한 번 (동전 문제라면 min 비교 한 번)
    • 저장된 답을 꺼내 보는 것(memo[n], dp[i])은 배열 칸을 바로 여는 것이라 한 번에 끝남
    • 그래서 DP의 일의 양은 어떤 문제든 이 공식 하나로 셀 수 있음: 채워야 할 칸 수 × 한 칸을 채우는 비용

    시간 복잡도 — 얼마나 오래 걸리는가?

    구현세는 것계단 10칸일 때계단 30칸일 때Big-O
    순수 재귀호출 횟수109번1,664,079번O(2ⁿ)
    메모이제이션 (탑다운)호출 횟수17번57번O(n)
    타뷸레이션 (바텀업)덧셈 횟수8번28번O(n)
    공간 최적화 (변수 2개)덧셈 횟수8번28번O(n)
    • O(2ⁿ)을 쉽게 말하면: 칸이 하나 늘 때마다 일이 몇 배씩 불어남 — 계단이 10칸 늘 때마다 호출이 약 120배 (10칸 109번 → 20칸 13,529번 → 30칸 1,664,079번)
      • 이유: 같은 작은 문제를 버리고 또 계산하기 때문 — 소문이 한 사람에게서 두 사람씩 퍼져 나가듯 호출이 가지를 치며 불어남
      • 7강 피보나치로 재도 같음: fibo(35) 한 번에 29,860,703번 호출
    • O(n)을 쉽게 말하면: 칸이 10배 늘면 일도 10배만 늘어남 — 표를 왼쪽에서 오른쪽으로 한 번 채우고 끝
      • 같은 fibo(35)도 메모이제이션은 69번, 타뷸레이션은 덧셈 34번, 공간 최적화는 덧셈 33번
    • 메모이제이션의 호출이 덧셈보다 조금 많은 이유: 수첩(memo)을 열어 보고 바로 돌아오는 호출도 1번으로 세기 때문 — 그래도 n에 비례
    • 계단 오르기는 입력 n이 정해지면 항상 같은 횟수만큼 일함 — 운이 좋은 경우·나쁜 경우의 차이가 없음
    • 동전 문제: 칸 수(금액 + 1) × 한 칸의 비용(동전 종류 수) = O(금액 × 동전 종류)
      • 예: 120원, 동전 3종 → 121칸 × 3 = 약 363번 비교

    공간 복잡도 — 메모리를 얼마나 더 쓰는가?

    • 순수 재귀: 표는 없지만, 아직 끝나지 않은 호출들이 차례를 기다리며 쌓임(호출 스택) — 가장 깊을 때 약 n개, O(n)
    • 메모이제이션: 수첩(memo) n칸 + 호출 스택, O(n) — n이 아주 크면 호출 스택이 넘칠(StackOverflow) 위험
    • 타뷸레이션: 표(dp) n + 1칸, O(n) — 반복문이라 호출 스택은 쓰지 않음
    • 공간 최적화: 직전 두 칸만 기억하는 변수 2개, O(1) — 계단이 아무리 길어도 메모리는 그대로
    • 동전 문제: 금액 + 1칸짜리 표, O(금액) — 먼 칸(dp[money - 100])을 참조하므로 변수 2개로 줄일 수 없음
    한 줄 정리 — 적어 두면 다시 계산하지 않는다
    • DP는 답을 적어 둘 표(메모리)를 조금 쓰는 대신 일의 양을 O(2ⁿ) → O(n)으로 줄임
    • 점화식이 직전 몇 칸만 본다면 그 표마저 변수 몇 개로 줄일 수 있음 (O(n) → O(1))

    알고리즘 특성 — 언제 무엇을 쓰는가?

    • DP는 "알고리즘"이 아니라 "기법": "저장하고 재사용한다"는 접근법 — 문제마다 점화식이 다르므로, 연습의 핵심은 코드가 아니라 점화식 3단계
    • 왜 항상 정답인가: 전이에서 가능한 모든 선택을 비교하므로, 점화식이 옳다면 답은 항상 최적 — 그리디처럼 "운 좋게 맞는" 것이 아님
    • 시간과 공간의 교환: O(2ⁿ)의 시간을 O(n)의 메모리와 맞바꿈 — 1강의 "데이터의 규칙을 알수록 빨라진다"가 "이미 푼 답을 알수록 빨라진다"로 확장된 것
    • 탑다운 vs 바텀업 고르기: 필요한 칸만 계산하고 싶으면 메모이제이션, n이 크거나 어차피 모든 칸이 필요하면 호출 스택을 안 쓰는 타뷸레이션
    • 한계: 칸(상태)이 너무 많으면 메모리가 먼저 부족해짐, 또 같은 작은 문제가 다시 나오지 않으면 적어 둬도 다시 쓸 일이 없어 이득이 없음

    문제 상황 — 그리디가 실패한 그 동전, DP로 다시

    • 10강의 마지막 장면: 이상한 나라의 자판기는 동전이 {1, 60, 100}원뿐
    • 120원을 거슬러 줄 때 그리디(큰 동전부터)는 100원을 덥석 집은 탓에 100 + 1×20 = 21개를 내놓음 — 최적은 60×2 = 2개
    • 이제 DP로 "모든 선택을 비교하고 기록한다"는 방식이 이 문제를 어떻게 구하는지 확인

    데이터 모델과 점화식 (코드보다 먼저!)

    • 데이터: 동전 종류 {100, 60, 1}, 목표 금액 amount
    • ① 정의: dp[money] = money원을 만드는 최소 동전 개수
    • ② 기저: dp[0] = 0 (0원은 동전 0개로 만든다)
    • ③ 전이: 마지막에 넣은 동전이 coin이었다면 그 전 상태는 money - coin. 따라서 dp[money] = min(dp[money - coin] + 1) — 모든 동전 coin에 대해 비교
    • 그리디와의 차이가 전이에 그대로 드러남 — 그리디는 "가장 큰 동전 하나"만 보지만, 이 점화식은 세 동전을 전부 넣어 보고 최소를 고름
    • 이 점화식은 dp[money - 100]처럼 먼 칸을 참조하므로 변수 2개 최적화는 불가능하고 표 전체가 필요
    Java CoinChangeDpApplication.java 
    public class CoinChangeDpApplication {

    /** "도달 불가능"을 나타내는 큰 값 (더해도 넘치지 않도록 절반으로) */
    static final int IMPOSSIBLE = Integer.MAX_VALUE / 2;

    /** 10강의 그리디: 큰 동전부터 최대한 많이 사용한다. */
    static int greedyCount(int amount, int[] coinsDesc) {
        int remaining = amount;
        int totalCount = 0;
        for (int coin : coinsDesc) {
            totalCount += remaining / coin;
            remaining = remaining % coin;
        }
        return totalCount;
    }

    /** DP: dp[money] = money원을 만드는 최소 동전 개수. 0원부터 표를 채운다. */
    static int[] buildDpTable(int amount, int[] coins) {
        int[] dp = new int[amount + 1];
        dp[0] = 0;                          // 기저 조건: 0원은 동전 0개
        for (int money = 1; money <= amount; money++) {
            dp[money] = IMPOSSIBLE;
            for (int coin : coins) {
                // 점화식: dp[money] = min(dp[money - coin] + 1)  (모든 동전을 비교)
                if (coin <= money && dp[money - coin] + 1 < dp[money]) {
                    dp[money] = dp[money - coin] + 1;
                }
            }
        }
        return dp;
    }

    /** 완성된 테이블을 역추적해 실제로 어떤 동전을 몇 개 썼는지 알아낸다. */
    static String reconstruct(int amount, int[] coinsDesc, int[] dp) {
        StringBuilder sb = new StringBuilder();
        int money = amount;
        for (int coin : coinsDesc) {
            int used = 0;
            // dp[money - coin]이 정확히 1 작다면, 이 동전은 최적해의 일부다
            while (coin <= money && dp[money - coin] == dp[money] - 1) {
                money -= coin;
                used++;
            }
            if (used > 0) {
                if (sb.length() > 0) {
                    sb.append(", ");
                }
                sb.append(coin).append("원 x ").append(used).append("개");
            }
        }
        return sb.toString();
    }

    public static void main(String[] args) {
        int[] coinsDesc = {100, 60, 1};     // 10강의 반례 동전: {1, 60, 100}
        int[] amounts = {80, 120, 180, 200};

        System.out.println("동전 {1, 60, 100}으로 거슬러 주기 — 그리디(10강) vs DP(11강)");
        System.out.println("금액   | 그리디 개수 | DP 최소 개수 | DP가 고른 조합");
        System.out.println("-------+------------+-------------+---------------------");

        for (int amount : amounts) {
            int greedy = greedyCount(amount, coinsDesc);
            int[] dp = buildDpTable(amount, coinsDesc);
            String combo = reconstruct(amount, coinsDesc, dp);
            System.out.printf("%-6d | %-10d | %-11d | %s%n",
                    amount, greedy, dp[amount], combo);
        }

        System.out.println();
        System.out.println("120원: 그리디는 100원을 먼저 집어 21개, DP는 모든 동전을 비교해 2개(60+60).");
        System.out.println("그리디는 지금의 최선만 보지만, DP는 점화식으로 모든 선택을 비교한다.");
    }
}

    /**
     * dp[i] = "i번 계단을 밟고 서 있기"까지의 최소 비용.
     * 바닥에서 첫 발은 0번 또는 1번 계단에 바로 올릴 수 있다.
     */
    static long[] buildDpTable(int[] cost) {
        int n = cost.length;
        long[] dp = new long[n];

        dp[0] = cost[0];                    // 기저 조건: 바닥에서 바로 밟는다
        dp[1] = cost[1];

        for (int i = 2; i < n; i++) {
            // 점화식: i-1번에서 1칸 오르거나, i-2번에서 2칸 오르거나 — 싼 쪽을 고른다
            dp[i] = cost[i] + Math.min(dp[i - 1], dp[i - 2]);
        }
        return dp;
    }

    /** 꼭대기(마지막 계단 다음)까지의 최소 비용 */
    static long minTotalCost(int[] cost) {
        long[] dp = buildDpTable(cost);
        int n = cost.length;
        // 꼭대기에는 마지막 계단(n-1)에서 1칸, 또는 그 아래(n-2)에서 2칸 올라 도착한다
        return Math.min(dp[n - 1], dp[n - 2]);
    }

    /** 검증용 완전 탐색(3강): i번 계단을 밟은 뒤 꼭대기까지의 모든 경로를 시도한다. */
    static long bruteForceFrom(int[] cost, int i) {
        if (i >= cost.length) {
            return 0;                       // 이미 꼭대기
        }
        long stepOne = bruteForceFrom(cost, i + 1);
        long stepTwo = bruteForceFrom(cost, i + 2);
        return cost[i] + Math.min(stepOne, stepTwo);
    }

    static long bruteForceMin(int[] cost) {
        return Math.min(bruteForceFrom(cost, 0), bruteForceFrom(cost, 1));
    }

    public static void main(String[] args) {
        int[][] tests = {
                {10, 15, 20},
                {1, 100, 1, 1, 1, 100, 1, 1, 100, 1},
                {10, 15}
        };

        for (int[] cost : tests) {
            long[] dp = buildDpTable(cost);
            long dpAnswer = minTotalCost(cost);
            long bruteAnswer = bruteForceMin(cost);
            System.out.println("계단 비용 " + java.util.Arrays.toString(cost));
            System.out.println("  DP 테이블   = " + java.util.Arrays.toString(dp));
            System.out.println("  DP 최소 비용 = " + dpAnswer
                    + ", 완전 탐색 검증 = " + bruteAnswer
                    + ", 일치 = " + (dpAnswer == bruteAnswer));
            System.out.println();
        }
    }
}

    구현 순서와 핵심 알고리즘 적용 부분

    1. 정의가 절반입니다. dp[i]를 "i번 계단을 밟고 서 있기까지의 최소 비용"으로 정의했기 때문에 전이가 cost[i] + min(...) 한 줄로 떨어집니다. "i번 계단을 지나가기까지"처럼 모호하게 정의하면 전이를 쓸 수 없습니다.
    2. 기저 조건: 첫 발은 0번 또는 1번에 바로 올릴 수 있으므로 dp[0] = cost[0], dp[1] = cost[1]. dp[1]에 dp[0]을 더하지 않는 것이 포인트입니다.
    3. 전이: i번 계단에 도착하는 직전 상태는 i-1번 아니면 i-2번뿐 — "마지막 걸음으로 나누기"라는 계단 오르기의 논리가 min으로 바뀌었을 뿐입니다.
    4. 답 읽기: 꼭대기는 계단이 아니므로 테이블 밖에 있습니다. 꼭대기 직전 상태(n-1 또는 n-2) 중 싼 쪽이 답입니다.
    5. 검증: 테스트 2에서 완전 탐색은 2^10 수준의 경로를 모두 확인해 6을 내고, DP는 덧셈·비교 몇 번으로 같은 6을 냅니다 — 정확성은 같고 일의 양만 다릅니다.

    복잡도 분석

    • DP: 테이블 n칸 × 칸당 O(1) = 시간 O(n), 공간 O(n) (변수 2개 최적화 시 공간 O(1)).
    • 완전 탐색: 경로 수가 피보나치처럼 늘어나 O(2ⁿ) — n=10,000 제한에서는 DP만 감당할 수 있습니다.

    자주 발생하는 오류

    • dp[1]을 cost[0] + cost[1]로 채우는 실수 — 첫 발은 1번 계단에 바로 올릴 수 있습니다.
    • 답을 dp[n - 1]로만 읽는 실수 — 마지막 계단을 밟지 않고 n-2에서 2칸 올라가는 더 싼 경로를 놓칩니다. (테스트 1이 이 경우: 답은 dp[2]=30이 아니라 dp[1]=15)
    • 반복 범위를 i <= n으로 써서 dp[n]에 접근 — 이 테이블은 크기가 n이므로 오류 2(테이블 크기)와 같은 예외가 납니다.

    다른 해결 방법

    같은 점화식을 탑다운(메모이제이션)으로도 구현할 수 있습니다. minCostFrom(i) = "i번 계단부터 꼭대기까지의 최소 비용"으로 정의하면 bruteForceFrom에 memo 배열만 붙인 형태가 됩니다 — 검증용 완전 탐색과 정답 DP가 사실 같은 식의 두 구현이라는 것을 확인해 보세요.

    15오늘의 핵심 정리

    • 동적 계획법(DP)은 작은 문제의 답을 저장하고 재사용하는 설계 기법이다. 성립 조건은 중복 부분 문제와 최적 부분 구조 두 가지.
    • 순수 재귀 피보나치는 n=35에서 29,860,703번 호출된다(실측). 답을 저장하면 69번 — O(2ⁿ)이 O(n)이 된다.
    • DP의 설계도는 점화식이며, 세우는 순서는 ① 정의(dp[i]를 문장으로) → ② 기저 조건 → ③ 전이다. 코드는 그다음이다.
    • 같은 점화식의 두 구현: 메모이제이션(탑다운, 재귀+저장)과 타뷸레이션(바텀업, 반복문+테이블). 기본은 바텀업.
    • 점화식이 직전 몇 칸만 참조하면 테이블을 변수 몇 개로 압축할 수 있다(공간 O(1)).
    • 그리디는 선택 하나를 확정하지만, DP는 점화식으로 모든 선택을 비교한다 — 그래서 동전 {1, 60, 100}의 120원에서 그리디는 21개, DP는 2개.
    • DP 테이블에는 최적값뿐 아니라 답을 복원할 정보도 들어 있다(역추적).
