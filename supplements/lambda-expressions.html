람다식

Lambda Expressions

자바 문법 보충 자료 Java 17+

람다식은 "메서드 하나를 값처럼 넘기는 문법"입니다. 13강의 코드는 알고리즘의 동작이 눈에 보이도록 반복문과 조건문으로 짜여 있습니다. 그 코드가 손에 익은 다음, 같은 로직을 훨씬 짧게 쓰는 방법이 자바에 있습니다. 이 문서는 그 첫 단계입니다. 여기서 배운 문법이 곧바로 4강의 Comparator와 5강의 검색 조건에 쓰입니다.

이 문서의 목차

    01왜 필요한가

    4강에서 상품 목록을 평점 내림차순으로 정렬했습니다. 정렬 알고리즘 자체는 insertionSort 하나로 충분했고, 바꾼 것은 "둘 중 누가 앞에 오는가"를 판단하는 규칙뿐이었습니다. 자바에서 이 규칙은 Comparator라는 인터페이스로 전달합니다.

    문제는 그 규칙을 넘기는 방법입니다. 람다식이 없던 시절에는 인터페이스를 구현한 이름 없는 클래스를 그 자리에서 만들어야 했습니다. 아래 두 코드는 하는 일이 완전히 같습니다.

    Java 이전 — 익명 클래스 (6줄) 
    Comparator<Product> byPrice = new Comparator<Product>() {
    @Override
    public int compare(Product a, Product b) {
        return Integer.compare(a.price, b.price);
    }
};
    Java 이후 — 람다식 (1줄) 
    Comparator<Product> byPrice = (a, b) -> Integer.compare(a.price, b.price);

    사라진 것을 하나씩 세어 봅시다. new Comparator<Product>(), @Override, public int compare, 매개변수 타입 Product 두 개, 중괄호, return. 전부 컴파일러가 이미 알고 있는 정보입니다. byPrice의 타입이 Comparator<Product>라고 선언된 순간, 구현해야 할 메서드가 compare라는 것도, 매개변수가 Product 둘이라는 것도 정해집니다. 람다식은 그 아는 것들을 다시 적지 않겠다는 문법입니다.

    람다식은 "새 기능"이 아니다

    람다식으로 할 수 있는 일은 익명 클래스로도 전부 할 수 있습니다. 바뀌는 것은 표현이지 능력이 아닙니다. 그래서 13강을 람다 없이 배워도 아무것도 잃지 않고, 나중에 람다로 바꿔도 알고리즘은 그대로입니다.

    02학습 목표

    이 문서를 읽고 나면 다음을 할 수 있습니다.

    • 학생은 람다식의 세 부분(매개변수, ->, 몸통)을 구분하여 읽을 수 있다.
    • 학생은 함수형 인터페이스가 무엇인지, 왜 추상 메서드가 하나여야 하는지 설명할 수 있다.
    • 학생은 Predicate, Function, Consumer, Supplier, Comparator를 상황에 맞게 고를 수 있다.
    • 학생은 익명 클래스로 작성된 코드를 람다식으로 바꿔 쓸 수 있다.
    • 학생은 람다식을 메서드 참조(::)로 더 줄일 수 있는 경우를 판단할 수 있다.
    • 학생은 지역 변수 캡처 규칙(effectively final)을 어겼을 때의 오류를 읽고 고칠 수 있다.

    03선수 지식

    이 문서는 다음을 이미 알고 있다고 가정합니다. 모두 13강 안에서 이미 쓰고 있는 것들입니다.

    항목필요한 수준처음 만난 곳
    메서드매개변수와 반환값을 읽고 쓸 수 있음1강
    인터페이스"메서드 목록만 정해 둔 약속"이라는 개념4강 Comparable
    제네릭List<String>처럼 타입을 꺾쇠에 적는 형태2강
    Comparatorcompare(a, b)의 반환값 의미(음수·0·양수)4강
    인터페이스가 아직 낯설다면

    인터페이스는 "이런 메서드를 가진 무언가"라는 약속입니다. Comparator는 "두 값을 받아 순서를 정하는 compare 메서드를 가진 무언가"라는 뜻이고, 정렬 메서드는 그 약속만 믿고 comp.compare(a, b)를 호출합니다. 누가 그 약속을 지키는지는 정렬 메서드의 관심사가 아닙니다 — 그래서 규칙을 갈아 끼울 수 있습니다.

    04문법 한눈에

    람다식은 언제나 세 부분입니다. 매개변수 목록, 화살표 ->, 몸통.

    Java 형태 다섯 가지 
    // 1) 매개변수 없음 — 괄호는 비워 두고 반드시 쓴다
Runnable hello = () -> System.out.println("안녕하세요");

// 2) 매개변수 하나 — 괄호를 생략할 수 있다
Predicate<String> isEmpty = s -> s.isEmpty();

// 3) 매개변수 둘 — 괄호가 필요하다
Comparator<Integer> asc = (a, b) -> Integer.compare(a, b);

// 4) 몸통이 식 하나 — 중괄호와 return을 함께 생략한다 (식의 값이 곧 반환값)
Function<Integer, Integer> square = n -> n * n;

// 5) 몸통이 여러 줄 — 중괄호를 쓰면 return을 직접 써야 한다
Function<int[], Integer> sum = arr -> {
    int total = 0;
    for (int v : arr) {
        total += v;
    }
    return total;          // 중괄호를 쓴 순간 return은 생략할 수 없다
};
    가장 흔한 실수 — 중괄호와 return은 한 몸

    n -> { n * n }은 컴파일되지 않습니다. 중괄호를 열었으면 return n * n;이라고 써야 합니다. 반대로 n -> return n * n;도 틀립니다 — 중괄호 없이 return을 쓸 수는 없습니다. "중괄호 없으면 return 없음, 중괄호 있으면 return 필수"로 외우면 편합니다.

    매개변수 타입은 대부분 생략합니다. 컴파일러가 대입되는 변수의 타입에서 추론하기 때문입니다. 다만 추론할 근거가 없을 때는 직접 적어야 합니다. 4강 코드에 (Product p) -> p.rating처럼 타입이 붙어 있는 이유가 이것입니다 — Comparator.comparingDouble(...)만 보고는 p가 무엇인지 알 수 없기 때문입니다.

    05함수형 인터페이스

    자바에는 "함수 타입"이라는 것이 따로 없습니다. 람다식도 결국은 객체입니다. 그렇다면 (a, b) -> Integer.compare(a.price, b.price)는 어떤 클래스의 어떤 메서드가 되는 걸까요?

    답은 대입하는 쪽의 타입이 정한다입니다. 그리고 그 타입은 추상 메서드가 정확히 하나인 인터페이스여야 합니다. 이런 인터페이스를 함수형 인터페이스라고 부릅니다. 메서드가 둘이면 람다식이 그중 무엇을 구현하는지 알 방법이 없으니 당연한 규칙입니다.

    Java 직접 만들어 보는 함수형 인터페이스 
    @FunctionalInterface          // 추상 메서드가 둘 이상이면 컴파일 오류로 알려 준다
interface ScoreRule {
    boolean test(int score);  // 추상 메서드는 이것 하나뿐
}

public class RuleDemo {
    // 규칙을 "값"으로 받는다 — 세는 방법은 하나, 세는 기준은 호출자가 정한다
    static int countBy(int[] scores, ScoreRule rule) {
        int count = 0;
        for (int s : scores) {
            if (rule.test(s)) {
                count++;
            }
        }
        return count;
    }

    public static void main(String[] args) {
        int[] scores = {88, 72, 95, 64, 79, 91};

        System.out.println("80점 이상: " + countBy(scores, s -> s >= 80));
        System.out.println("60점 미만: " + countBy(scores, s -> s < 60));
        System.out.println("짝수 점수: " + countBy(scores, s -> s % 2 == 0));
        // countBy는 한 번도 고치지 않았다. 바뀐 것은 넘긴 규칙뿐이다.
    }
}

    2강의 countAtLeast(data, threshold)를 떠올려 보세요. 그 메서드는 "~점 이상"이라는 기준이 코드에 박혀 있어서 "짝수만 세기"가 필요해지면 메서드를 하나 더 만들어야 했습니다. 위 countBy는 기준 자체를 인자로 받으므로 한 번만 만들면 됩니다. 이것이 람다식이 실제로 바꾸는 것입니다 — 문법이 짧아지는 것은 부수 효과입니다.

    @FunctionalInterface는 안전벨트다

    이 애너테이션이 없어도 추상 메서드가 하나면 함수형 인터페이스로 동작합니다. 붙이는 이유는 나중에 누가 메서드를 하나 더 추가했을 때 그 자리에서 컴파일 오류를 내기 위해서입니다. 그것이 없으면 이 인터페이스를 람다로 쓰던 코드 전부가 대신 깨집니다.

    06표준 인터페이스

    위처럼 매번 인터페이스를 만들 필요는 없습니다. 자주 쓰는 형태는 자바가 java.util.function 패키지에 미리 만들어 두었습니다. "입력이 몇 개이고 출력이 있는가"만 보고 고르면 됩니다.

    인터페이스 메서드 입력 → 출력 쓰는 자리
    Predicate<T>test(T)1개 → boolean거르기 조건 (5강 검색)
    Function<T, R>apply(T)1개 → 값값 변환 (점수 → 등급)
    Consumer<T>accept(T)1개 → 없음출력·저장 등 소비
    Supplier<T>get()없음 → 값기본값·지연 생성
    Comparator<T>compare(T, T)2개 → int정렬 기준 (4강)
    BinaryOperator<T>apply(T, T)2개(같은 타입) → 같은 타입누적·합치기
    Runnablerun()없음 → 없음실행할 동작 자체
    Java 다섯 가지를 한 화면에서 
    import java.util.function.*;

Predicate<Integer>        pass    = s -> s >= 60;
Function<Integer, String> toGrade = s -> s >= 90 ? "A" : s >= 80 ? "B" : "C";
Consumer<String>          print   = msg -> System.out.println("> " + msg);
Supplier<String>          empty   = () -> "(값 없음)";
BinaryOperator<Integer>   add     = (a, b) -> a + b;

System.out.println(pass.test(72));       // true
System.out.println(toGrade.apply(85));   // B
print.accept("처리 완료");                // > 처리 완료
System.out.println(empty.get());         // (값 없음)
System.out.println(add.apply(3, 4));     // 7
    기본형에는 전용 인터페이스를 쓴다

    Predicate<Integer>는 int를 쓸 때마다 Integer로 포장했다가 다시 꺼냅니다(박싱·언박싱). 원소가 수십만 개인 배열에서는 이 비용이 눈에 띕니다. 그래서 IntPredicate, IntFunction, ToIntFunction처럼 기본형 전용 인터페이스가 따로 준비되어 있습니다. 1강에서 배운 "같은 결과라도 일의 양은 다를 수 있다"가 여기에도 그대로 적용됩니다.

    07강의 코드 바꿔 보기

    이제 실제 강의 코드를 바꿔 봅니다. 세 쌍 모두 왼쪽과 오른쪽의 동작이 완전히 같습니다. 결과가 달라지는 곳은 한 군데도 없습니다.

    ① 4강 — 정렬 기준

    Java ProductSortApplication — 이전 · 이후 
    // ── 이전: 익명 클래스로 기준을 만든다
Comparator<Product> byRatingDesc = new Comparator<Product>() {
    @Override
    public int compare(Product a, Product b) {
        int byRating = Double.compare(b.rating, a.rating);   // 내림차순이라 b가 앞
        if (byRating != 0) {
            return byRating;
        }
        return a.name.compareTo(b.name);                     // 동점이면 이름순
    }
};

// ── 이후: 람다 + Comparator의 조립 메서드
Comparator<Product> byRatingDesc =
        Comparator.comparingDouble((Product p) -> p.rating)
                  .reversed()
                  .thenComparing(p -> p.name);

// 정렬 호출은 양쪽 모두 그대로다
insertionSort(products, byRatingDesc);

    reversed()와 thenComparing()에 주목하세요. 익명 클래스 버전에서는 "내림차순"과 "동점 처리"가 compare 안에 뒤섞여 있어 읽으면서 부호를 따져 봐야 했습니다. 람다 버전은 "평점으로 비교 → 뒤집기 → 동점이면 이름으로"가 순서대로 읽힙니다. 코드가 짧아진 것보다 이쪽이 중요합니다.

    ② 5강 — 검색 조건

    Java BookSearch — 조건마다 메서드를 만들던 코드 
    // ── 이전: 조건이 늘 때마다 메서드가 하나씩 늘어난다
static int findByTitle(Book[] books, String title) {
    for (int i = 0; i < books.length; i++) {
        if (books[i].title.equals(title)) return i;
    }
    return -1;
}
static int findByAuthor(Book[] books, String author) { /* 거의 같은 코드 */ }
static int findCheaperThan(Book[] books, int price)  { /* 거의 같은 코드 */ }

// ── 이후: 순회는 한 번만 쓰고, 조건은 Predicate로 받는다
static int findFirst(Book[] books, Predicate<Book> match) {
    for (int i = 0; i < books.length; i++) {
        if (match.test(books[i])) return i;   // 5강 순차 탐색 그대로 — O(n)
    }
    return -1;
}

int a = findFirst(books, b -> b.title.equals("자료구조"));
int b2 = findFirst(books, b -> b.author.equals("김인하"));
int c = findFirst(books, b -> b.price < 20000);
    알고리즘은 바뀌지 않았다

    findFirst는 여전히 순차 탐색 O(n)입니다. 람다를 썼다고 이진 탐색이 되지는 않습니다. 5강의 핵심인 "정렬해 두면 O(log n)으로 줄일 수 있다"는 문법과 아무 상관이 없는 별개의 이야기입니다. 이 구분을 놓치지 마세요.

    08메서드 참조

    람다식의 몸통이 "이미 있는 메서드를 그대로 한 번 호출하는 것"뿐이라면 ::로 더 줄일 수 있습니다. 이것을 메서드 참조라고 합니다.

    종류람다식메서드 참조
    정적 메서드s -> Integer.parseInt(s)Integer::parseInt
    특정 객체의 메서드s -> out.println(s)out::println
    임의 객체의 메서드s -> s.toUpperCase()String::toUpperCase
    생성자() -> new ArrayList<>()ArrayList::new
    Java 줄여도 되는 경우와 안 되는 경우 
    // 줄일 수 있다 — 받은 값을 그대로 한 번 넘길 뿐이다
list.forEach(s -> System.out.println(s));
list.forEach(System.out::println);

// 줄일 수 있다 — Comparator.comparing에 넘길 "키를 뽑는 방법"이 곧 메서드다
Comparator<Product> byName = Comparator.comparing(p -> p.getName());
Comparator<Product> byName2 = Comparator.comparing(Product::getName);

// 줄일 수 없다 — 받은 값에 무언가를 더 하고 있다
list.forEach(s -> System.out.println("[" + s + "]"));

// 줄일 수 없다 — 인자의 순서나 개수가 다르다
Comparator<Product> desc = (a, b) -> Integer.compare(b.price, a.price);
    판단 기준 하나

    "람다의 매개변수가 메서드 호출에 그대로, 순서대로, 전부 들어가는가?" 그렇다면 메서드 참조로 줄일 수 있습니다. 하나라도 아니면 람다로 두세요. 억지로 줄인 메서드 참조는 오히려 읽기 어렵습니다.

    09자주 하는 실수

    ① 람다 안에서 지역 변수를 바꾸려 한다

    Java 컴파일 오류가 나는 코드 
    int count = 0;
list.forEach(s -> count++);   // 오류: local variables referenced from a lambda
                              //       expression must be final or effectively final

    람다는 지역 변수를 복사해서 가져갑니다. 원본이 나중에 바뀌면 복사본과 어긋나므로, 자바는 아예 "바뀌지 않는 변수만 가져갈 수 있다"고 정했습니다. final이라고 적지 않았어도 한 번 대입한 뒤 바꾸지 않으면 조건을 만족합니다(effectively final). 세는 것이 목적이라면 배열 한 칸이나 카운터 객체를 쓰거나, 애초에 count()·filter() 같은 방법을 쓰는 것이 낫습니다 (자바 스트림 문서에서 다룹니다).

    ② 익명 클래스와 this가 같다고 생각한다

    익명 클래스 안의 this는 그 익명 클래스 자신을 가리킵니다. 람다 안의 this는 람다를 감싼 바깥 객체를 가리킵니다. 익명 클래스를 람다로 바꾸다가 this가 섞여 있으면 의미가 조용히 달라집니다. 람다에는 자기 자신이라는 것이 없기 때문입니다 — 그래서 재귀 호출도 못 합니다.

    ③ 검사 예외를 그대로 던진다

    Predicate.test의 선언에는 throws가 없습니다. 그래서 람다 몸통에서 IOException 같은 검사 예외를 던지면 컴파일되지 않습니다. 람다 안에서 try-catch로 잡아 처리하거나, 예외를 던지지 않는 형태로 로직을 나눠야 합니다.

    ④ 짧다는 이유로 모든 것을 람다로 만든다

    람다는 이름이 없습니다. 이름이 없다는 것은 설명이 없다는 뜻이고, 스택 트레이스에도 lambda$main$0처럼 찍힙니다. 세 줄이 넘어가거나 로직에 이름을 붙일 수 있다면 이름 있는 메서드로 빼고 메서드 참조로 넘기는 편이 읽기에도 디버깅에도 낫습니다.

    연습 — 다음 익명 클래스를 람다식으로, 가능하면 메서드 참조로 바꿔 보세요
    Java 문제 
    Comparator<String> byLength = new Comparator<String>() {
    @Override
    public int compare(String a, String b) {
        return Integer.compare(a.length(), b.length());
    }
};

    답 — 세 단계로 줄어듭니다.

    Java 답 
    // 1) 람다식으로
Comparator<String> byLength = (a, b) -> Integer.compare(a.length(), b.length());

// 2) "키를 뽑는 방법"만 주는 형태로
Comparator<String> byLength = Comparator.comparingInt(s -> s.length());

// 3) 그 방법이 이미 메서드이므로 메서드 참조로
Comparator<String> byLength = Comparator.comparingInt(String::length);

    10확인 퀴즈

    문법보다 "언제 쓰는가"를 확인하는 문제들입니다.

    11핵심 정리

    • 람다식은 매개변수 · -> · 몸통 세 부분이다. 중괄호를 쓰면 return이 필수, 안 쓰면 식의 값이 곧 반환값이다.
    • 람다식이 대입될 수 있는 타입은 추상 메서드가 하나뿐인 인터페이스(함수형 인터페이스)다. 무엇을 구현하는지 정해지려면 하나여야 한다.
    • 자주 쓰는 형태는 Predicate(거르기), Function(변환), Consumer(소비), Supplier(공급), Comparator(정렬)로 이미 준비되어 있다.
    • 람다가 실제로 바꾸는 것은 길이가 아니라 "기준을 값으로 넘길 수 있다"는 점이다. 순회 코드 하나로 여러 조건을 처리할 수 있게 된다.
    • 몸통이 기존 메서드 호출 하나뿐이면 메서드 참조 ::로 더 줄인다. 인자를 그대로·순서대로·전부 넘길 때만이다.
    • 람다가 가져가는 지역 변수는 바뀌지 않아야 한다(effectively final). 값을 누적하려면 다른 방법을 써야 한다.
    • 문법이 알고리즘을 바꾸지는 않는다. 순차 탐색은 람다로 써도 O(n)이다. 복잡도는 13강에서 배운 그대로다.

    12다음 단계

    람다식은 "동작 하나를 값으로 만드는 법"입니다. 그 값들을 여러 개 이어 붙여 데이터 처리의 한 줄기로 만드는 도구가 스트림입니다. filter에 넘기는 것이 Predicate, map에 넘기는 것이 Function, sorted에 넘기는 것이 Comparator — 방금 배운 것들이 그대로 재료가 됩니다.

    2강의 성적 집계와 3강의 단어 빈도 계산을 for 반복문 없이 다시 쓰는 방법은 자바 스트림 문서에서 이어집니다.

    순서 권장

    스트림 문서는 이 문서의 내용을 알고 있다고 가정합니다. 람다식 → 스트림 순서로 읽으세요. 반대로 읽으면 filter(s -> s >= 60)의 괄호 안이 무엇인지부터 막힙니다.
